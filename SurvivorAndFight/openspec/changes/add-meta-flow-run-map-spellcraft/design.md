# Design: 元流程、跑图与法术编程

## Context
本变更跨壳层 UI、程序化地图、局内战斗施法管线；与既有 ECS、子弹、技能、升级系统存在集成点。交付须支持多人并行实现，并在接口冻结后独立合并。

## Goals
- 建立从启动到单局跑图再到战斗的确定性状态机与数据契约。
- 跑图每局随机生成三大关，图结构为有向无环图，节点类型可配置扩展。
- 法杖系统限定同时三支；槽位装配产生可执行的施放描述，由现有战斗管线消费。
- 配表、注册表与代码中的静态常量分层：`src/defines/` 放默认值与枚举；数值与内容主数据放 JSON；注册关系写入 `tables.registry.json`。

## Non-Goals
- 本变更不要求实现与商业游戏完全一致的数值平衡；数值仅须可配置与可回放。
- 本变更不要求实现完整物理交互式法术世界（Noita 体素化学）；仅实现槽位链式组合与现有发射管线对接。
- 本变更不要求网络同步与服务器存档；单机内存存档策略在接口层预留钩子即可。

## Decisions
- **决策：跑图为一局 Run 的子状态**：`RunId` 与随机种子在选局确认时生成；跑图状态机持有当前节点与可达集合。
- **决策：三大关顺序锁定**：Act1 → Act2 → Act3；每 Act 内层与分叉随机；跨 Act 迁移通过 Boss 或强制出口节点触发（具体节点类型由配表声明）。
- **决策：法杖施放求值输出「施放描述」结构**：不直接在求值阶段创建实体；由战斗帧循环或技能系统消费施放描述并生成子弹或效果请求。
- **决策：修饰器装配规则用 schema 表达**：每种子弹槽声明允许的修饰器标签集合；不兼容组合在装配阶段拒绝并返回错误码。

## Multitask agent scheduling
多智能体调度策略以 `WORKSTREAMS.md` 为权威：按工作流拆分所有权、依赖与 artifact；每个工作流入口须读取 `INTERFACES.md` 冻结字段；禁止跨工作流在未冻结字段上并行修改。

## Risks / Trade-offs
- **风险：法术组合与现有子弹系统耦合加深** → **缓解**：施放描述作为唯一边界类型；子弹系统只依赖描述字段，不依赖 UI 或跑图。
- **风险：跑图生成缺陷导致死锁或无出口** → **缓解**：生成器执行终点可达性与 DAG 校验；失败时整图重 roll，重试次数上限写在配表。
- **风险：并行实现接口漂移** → **缓解**：变更合入前对照 `INTERFACES.md` 做契约检查；契约变更必须同步更新本变更下 spec 增量。

## Migration Plan
- 新代码路径与旧入口并存：旧入口须仍能进入战斗调试场景；元流程入口由 `MetaFlowController` 统一注册。
- 配表新增不得破坏既有表加载；未提供的表项使用 define 默认值路径须在加载器层显式声明。

## Open Questions
- **终点节点形状**：默认约定每 Act 终端为单一 Boss 节点；若配表未声明 Boss，则使用强制出口节点完成 Act。实现须在生成器内校验至少一条通往终端的路径。
- **问号事件内容**：默认使用独立事件池表驱动；事件池未配置时，问号节点降级为普通战斗节点，降级行为写入日志。
