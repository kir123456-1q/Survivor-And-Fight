## Context
项目需要一个可维护的 UI 架构来支撑复杂界面流程。目标是以 MVC 统一 UI 模块结构，通过 UI 栈管理界面路由与返回行为，使用红点树承载跨模块提示状态，并通过自动对象池减少频繁创建销毁带来的性能波动。

## Goals / Non-Goals
- Goals:
  - 定义可执行的 MVC 生命周期协议（创建、显示、隐藏、销毁）与初始化顺序。
  - 建立 UI 栈管理契约，确保界面导航可预测且行为一致。
  - 建立红点树模型，支持父子聚合和按需刷新。
  - 定义自动对象池策略，使 UI 节点在生命周期内可复用并可安全回收。
- Non-Goals:
  - 不在本提案中绑定具体业务 UI 页面实现。
  - 不在本提案中定义视觉规范、动画规范或美术资源流程。
  - 不替代现有配置系统，只约束 UI 框架能力。

## Decisions
- Decision: 采用“生命周期驱动 + 管理器协作”的架构。
  - MVC 生命周期由 UI 模块显式实现，UI 栈、红点树、对象池由独立服务协作完成。
  - 初始化顺序定义为：构造 -> 依赖注入 -> 初始化 -> 入栈显示，回收顺序与之对称。
- Decision: UI 栈作为唯一界面路由真相源。
  - 所有全屏界面切换通过栈操作驱动，禁止绕开栈直接操纵可见性。
  - 支持 push/pop/replace/clearToRoot 等标准语义，降低多入口跳转歧义。
- Decision: 红点树采用增量更新和聚合缓存。
  - 叶子节点接收业务状态，父节点通过聚合策略计算（如 OR/COUNT）。
  - 通过事件总线通知 UI 层，仅刷新受影响路径，避免全量遍历。
- Decision: 对象池采用自动托管策略。
  - UI 模块释放时由池服务按规则自动决定回收/销毁。
  - 池对象需执行重置钩子，防止状态泄漏（监听、计时器、动画、引用）。

## Risks / Trade-offs
- 统一由栈控制会限制部分历史直连写法，需要改造旧调用路径。
  - Mitigation: 提供过渡适配层，将旧接口映射到栈操作并加日志告警。
- 红点树节点过多时可能导致更新路径复杂。
  - Mitigation: 限制树深、建立节点命名规范，并采用路径级增量刷新。
- 自动池化可能引入脏状态复用问题。
  - Mitigation: 定义强制重置协议与复用前校验，校验失败则降级销毁重建。

## Migration Plan
1. 增加 MVC 生命周期接口与基类，完成最小骨架。
2. 引入 UI 栈管理器并改造关键入口页面到栈流程。
3. 引入红点树服务并接入典型菜单导航链路。
4. 引入 UI 对象池服务，先在高频开关界面灰度启用。
5. 补充监控日志（栈深、池命中、红点更新耗时）并逐步全量切换。

## Open Questions
- 浮窗类 UI（非全屏、可并行显示）是否使用独立子栈或分层栈模型？
- 红点聚合是否需要支持权重与优先级，而不仅是布尔/计数模式？
