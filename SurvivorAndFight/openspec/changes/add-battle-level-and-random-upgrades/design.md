## Context
当前项目已具备 ECS 基础、属性系统、技能效果与子弹系统，并已完成玩家/怪物基础对抗闭环。  
现有战斗短板主要集中在成长与构筑层：
- 缺少“经验-等级-选择-构筑”的长期循环；
- 子弹系统虽支持 damage/speed/duration/penetration，但仍是单次固定读取，缺少“运行时成长叠加模型”；
- 缺少升级选择 UI 流程定义，无法形成明确的玩家决策反馈。

## Goals / Non-Goals
- Goals:
  - 建立等级成长与随机升级机制，形成战斗中期和后期策略空间。
  - 升级能力覆盖子弹类型、数量、穿透和核心战斗数值。
  - 在不推翻现有战斗系统的前提下扩展，优先增量改造已有模块。
  - 明确文件与美术资源边界，降低后续实现阶段的不确定性。
- Non-Goals:
  - 本提案不定义完整经济系统（商店、货币、天赋树）。
  - 本提案不引入联机/同步逻辑。
  - 本提案不强制一次性实现所有子弹表现，仅要求机制可扩展。

## Decisions
- Decision: 使用“战斗运行时成长态（Runtime Combat Upgrade State）”统一承载升级结果。
  - Why: 避免将升级直接写死在 `BulletSystem` 或技能逻辑中，降低耦合。
  - Alternatives considered:
    - 直接修改子弹表行数据：实现快，但运行时回滚与多来源叠加困难。
    - 在每个系统单独维护 buff：灵活但数据分散，排查困难。

- Decision: 升级候选由配表驱动，运行时按权重随机并过滤不可选项。
  - Why: 便于策划迭代，支持前置条件、互斥和重复上限。
  - Alternatives considered:
    - 纯代码随机池：迭代成本高，维护风险高。

- Decision: 升级选择时暂停战斗逻辑帧（或降低到 0 速），确认后恢复。
  - Why: 保证可读性和操作确定性，避免升级期间被击杀。
  - Alternatives considered:
    - 不暂停：节奏更紧，但对当前 UI 与输入体系负担大。

## Risks / Trade-offs
- 风险: 升级项过多会引发组合爆炸，平衡成本上升。  
  - Mitigation: 引入标签化升级池与分层解锁（early/mid/late）。
- 风险: 多子弹与穿透提升可能导致性能压力。  
  - Mitigation: 结合 `BulletPool`、发射上限、屏幕内子弹上限与回收策略。
- 风险: 新子弹类型依赖新增美术，阻塞功能联调。  
  - Mitigation: 使用占位预制体与通用图标优先打通机制，再迭代表现。

## Migration Plan
1. 先落地升级相关配表与运行时状态组件。
2. 接入经验获取与升级触发，再接入 3 选 1 面板流程。
3. 将升级效果应用到发射参数与子弹实例参数。
4. 最后替换占位资源为正式美术资源并调参与验收。

## Open Questions
- 经验来源是否仅限击杀怪物，是否包含存活时间与连杀奖励？
- 升级候选数量是否固定 3 个，是否支持后续道具改造为 4~5 选？
- 新子弹类型的首批清单是否固定为 2~3 种，还是按美术资源准备情况动态上线？
