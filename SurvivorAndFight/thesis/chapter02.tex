\chapter{相关技术与理论基础}
\label{chap:related}

本章从\textbf{引擎与语言}、\textbf{玩法与逻辑架构}、\textbf{界面架构}三条主线，说明 Survivor And Fight 所依托的技术选型及其理论依据，为第三、四章的需求与设计提供共同语境。各节在综述文献与业界实践的基础上，给出本项目在毕业设计规模下的取舍理由，避免将实现细节堆砌为孤立名词列表。

\section{引擎语言选择}
\label{sec:engine-lang}

\subsection{H5 游戏引擎选型}

面向浏览器分发的 2D 游戏，常见技术路线包括基于 Canvas/WebGL 的轻量渲染库（如 Phaser、PixiJS）以及一体化游戏引擎（如 Cocos Creator、LayaAir）。前者灵活度高，但场景管理、预制体工作流、UI 与资源打包往往需自行拼装；后者提供 IDE、预制体实例化、帧循环与输入封装，更适合在有限周期内交付可演示闭环\cite{goslin2004panda,gregory2018game}。

本项目选用 \textbf{LayaAir 3.x}，主要基于以下考虑：（1）课程与实验室技术栈已积累 Laya 工程经验，降低环境搭建成本；（2）3.x 对 TypeScript 的一等支持与本项目源码语言一致；（3）2D 预制体、\texttt{Area2D} 与 UI2 组件（\texttt{GBox}、\texttt{GButton} 等）可满足元菜单、跑图与战斗 HUD 的界面需求；（4）内置预览与发布至 \texttt{bin/} 的流程便于性能测试与答辩演示。Gregory 指出，商业引擎的价值在于将渲染、资源、场景更新与脚本生命周期统一管理\cite{gregory2018game}；LayaAir 在 H5 场景下承担了类似“运行时平台”的角色。

与 Unity、Unreal 等原生引擎相比，H5 方案的分发成本更低，但受浏览器单线程模型与 GC 行为约束更明显。Ullmann 等对游戏引擎子系统耦合的研究表明，无论引擎种类，清晰划分“引擎层—游戏逻辑层”均有利于后期维护\cite{ullmann2023coupling}。因此本项目将 Laya 节点仅作为\textbf{表现层}，核心玩法放在自研轻量 ECS 中更新，而非把所有逻辑写入 \texttt{Laya.Script} 回调。

\subsection{TypeScript 与工程常量管理}

脚本语言选用 \textbf{TypeScript}，在 JavaScript 基础上提供静态类型与模块化，便于在实体、组件、系统数量增长时保持接口稳定。Briand 等关于面向对象设计可维护性的实验表明，清晰的模块边界与一致的命名有助于降低理解成本\cite{briand2001maintainability}。本项目将可调战斗常量、UI 阈值、路径正则等\textbf{静态配置}集中于 \texttt{src/defines/}，经 \texttt{index.ts} 统一导出，避免在业务文件顶部散落魔法数；策划向的数值则外置 JSON 配表（见第~\ref{sec:gameplay-arch}~节），实现“工程常量”与“策划参数”的分工。

\subsection{主循环、预制体与引擎使用约束}

游戏主循环由 \texttt{Laya.timer.frameLoop} 驱动：每帧先执行 \texttt{EcsWorld.update(deltaTime)} 更新逻辑，再由引擎完成渲染与 UI 事件分发，符合 Gregory 所述“逻辑 tick 与绘制分离”的常见模式\cite{gregory2018game,unitymanual2016}。入口脚本 \texttt{Main.ts} 挂载在 \texttt{Area2D} 子节点而非 3D 根节点，避免纯 2D 战斗 Demo 误入 3D 渲染管线，属于针对本项目的引擎裁剪实践。

使用 Laya API 时须统一 \texttt{Laya.} 前缀（如 \texttt{Laya.Sprite}、\texttt{Laya.Handler.create}）。角色与子弹通过 \texttt{Laya.Prefab.instantiate} 生成；\textbf{可加载资源}（材质、贴图、预制体）须置于 \texttt{assets/} 发布目录，不可放在 \texttt{src/}，否则预览时会出现路径解析失败。2D 节点位移须通过 \texttt{transform.position = new Laya.Vector3(...)} 或 \texttt{translate} 完成，不可对 \texttt{position} getter 返回的副本调用 \texttt{setValue}，否则会出现逻辑坐标已变但画面不动的隐蔽错误——该问题在俯视角相机跟随与怪物追逐调试中曾多次出现，写入本文以供后续开发者规避。

\section{项目玩法架构选择}
\label{sec:gameplay-arch}

\subsection{Survivor-like 品类与核心循环}

Survivor-like 游戏的核心循环可形式化为：\emph{移动躲避} $\rightarrow$ \emph{自动输出伤害} $\rightarrow$ \emph{击杀获取经验} $\rightarrow$ \emph{升级强化 Build} $\rightarrow$ \emph{更高密度敌人}。与传统射击游戏相比，玩家认知负荷从“瞄准射击”转向“走位与构筑决策”\cite{gregory2018game}。因此，客户端架构必须同时满足：（1）玩家持续移动时，碰撞与伤害结算仍稳定、可预期；（2）数分钟内多次升级，奖励能即时写入属性或技能栏；（3）技能数值可通过配表迭代，而不反复修改核心战斗代码。

本项目在 \texttt{SimpleEcsDemo} 中默认创建玩家实体并由 \texttt{PlayerAutoCastSystem} 自动施法，保留 \texttt{ControlSystem} 处理走位，以降低操作门槛、突出构筑玩法。经验获取由 \texttt{ExperienceSystem} 完成，击杀奖励与等级加成通过 \texttt{defines} 中 \texttt{MONSTER\_EXP\_REWARD\_BASE}、\texttt{MONSTER\_EXP\_REWARD\_LEVEL\_BONUS} 等常量调节，属于可配置的“节奏设计”而非硬编码逻辑。

\subsection{轻量实体组件系统（ECS）}

\textbf{实体组件系统（ECS）}将游戏对象拆为实体标识（Entity）、纯数据组件（Component）与无状态系统（System）。其工程收益在于：新增怪物行为时往往只需增加 System 或扩展组件字段，而无需维护庞大的继承树；数据布局也有利于按类型批量处理\cite{gregory2018game}。

Unity DOTS 路线采用 ECS + Job System + Burst，面向数万实体级并行\cite{gregory2018game}。毕业设计团队规模与周期有限，若引入完整 DOTS 等价物，学习与 Laya 节点绑定的成本过高。本项目采用\textbf{教学向轻量 ECS}：\texttt{EntityId} 为数值类型；\texttt{ComponentStore} 按组件类型使用 \texttt{Map} 存储；\texttt{EcsWorld.update} 单线程顺序调用已注册系统，并按 \texttt{input/logic/physics/render} 分组排序。第 1 期目标为“结构清晰、支撑数百同屏实体”，而非追求极致数据导向布局。

玩法层组件包括 \texttt{PlayerTag}/\texttt{MonsterTag}、\texttt{Position}/\texttt{Velocity}、\texttt{Attribute}（含可溯源 modifier）、\texttt{Skill}、\texttt{SkillLoadoutState} 等；系统包括 \texttt{MovementSystem}、\texttt{AttributeSystem}、\texttt{SkillSystem}、\texttt{BulletSystem}、\texttt{MonsterChaseSystem} 等。\texttt{FilterRegistry} 提供 \texttt{Players}、\texttt{Monsters} 等命名筛选，避免各 System 重复编写交集查询。怪物与玩家共享位移、属性、技能等组件，仅通过标签区分，体现\textbf{组合优于继承}的原则。

\subsection{数据驱动与 JSON 配表}

Roguelite 与动作游戏普遍采用\textbf{数据驱动}：将冷却、伤害、子弹参数、效果链等外置为表，由运行时加载\cite{gregory2018game}。常见实现方式包括：（1）运行时加载 JSON 并反射填充数据类；（2）构建期生成 TypeScript 常量；（3）注册表声明表结构、运行时按路径加载。本项目采用第（3）种：\texttt{tables.registry.json} 声明表名与文件，\texttt{ConfigBootstrap.ensureGameConfigLoaded()} 在启动时加载，\texttt{initData} 将行挂载至 \texttt{Data.Character}、\texttt{Data.Skill} 等命名空间。

技能语义拆分为 \texttt{Skill} 与多行 \texttt{SkillEffect}：每行对应子弹、穿透/分裂/连锁修饰或直伤之一，由 \texttt{EffectExecutor} 按顺序解释——修饰器须位于后续 \texttt{bullet} 效果之前，形成链式组合。伤害字符串（如 \texttt{"atk*1.5+10"}）由 \texttt{FormulaParser} 在白名单运算下解析，禁止 \texttt{eval} 以防配表被篡改时产生代码注入风险。\texttt{Targeting} 支持自动索敌与简单指向输入，满足自动施法与后续扩展。

与可视化脚本相比，JSON 配表便于 Git 管理与差异审查；代价是部分错误推迟到集成阶段发现，因此项目以 \texttt{isGameConfigReady} 与单元验证脚本（公式、属性修饰器）作为质量门禁。

\subsection{Roguelite 跑图与关卡结构}

除单局战斗外，元游戏采用\textbf{Slay the Spire 式 DAG 跑图}：每局生成三个 Act，每 Act 为多层有向无环图，节点类型包括休息、普通战斗、Boss、宝藏等\cite{gregory2018game}。地图生成一般包含分层、节点抽样、连边约束与可达性校验；本项目 \texttt{RunMapGenerator} 实现固定行数网格、末行 Boss、中间随机分叉，并通过 \texttt{validateActReachBoss} 保证 Boss 可达。失败时回退保底图，避免进度卡死。

\texttt{SeededRng} 使相同种子可复现地图，便于录制答辩视频与回归测试。\texttt{MetaFlowController} 在用户确认节点后触发 \texttt{onEnterCombat}，将节点载荷（如 Boss 关更长生存时间）传入战斗场景，实现元游戏与局内逻辑的松耦合。

\subsection{战斗性能与密集实体仿真}

Survivor-like 后期同屏怪物与弹幕数量陡增，H5 客户端热点包括：每帧大量碰撞检测、预制体反复实例化触发 GC、主线程追逐与分离计算。业界常见对策包括对象池、纹理合批、逻辑暂停与将纯数值计算迁至 Web Worker\cite{gregory2018game,mckenzie2008crowd}。

本项目 \texttt{BulletPool}、\texttt{MonsterPool} 按预制体路径分桶复用节点；\texttt{BulletHitTest} 使用距离平方比较减少开方；\texttt{GameSession.paused} 在技能面板打开时早退战斗 System。当实体数达到阈值时，\texttt{CombatDataPrepareSystem} 将坐标等快照经 \texttt{CombatDataBridge} 提交 Worker，在共享的 \texttt{combatWorkerLogic.ts} 中计算追逐、分离与摆动，主线程再写回速度；\textbf{子弹碰撞}因依赖 Laya 节点与阵营判定，仍保留在主线程。Cantrell 等在 Unity 中实现物理人群疏散时同样强调“重计算与交互渲染分离”\cite{cantrell2018unity}；Helbing 等关于恐慌人群的研究则提示，密集场景须关注分离力与局部稳定性\cite{helbing2000panic}，与本项目 \texttt{MonsterChaseSystem} 中的分离项设计相呼应。

上述选型使玩法架构在“可扩展”与“可测”之间取得平衡：ECS 与配表支撑内容迭代，池化与 Worker 支撑同屏规模，跑图 DAG 支撑元游戏节奏。

\section{UI 架构选择}
\label{sec:ui-arch}

\subsection{MVC 分层与全屏界面栈}

游戏 UI 常见模式包括 MVC、MVP、MVVM 等\cite{heijstek2011empirical}。Heijstek 等通过实验比较架构描述的图文形式，指出结构化图示有助于理解系统边界；本项目在实现上采用\textbf{MVC 变体}：

\begin{itemize}
  \item \textbf{Model}：来自 ECS 组件（如 hp、装配状态）或独立模型类（如 \texttt{RunMapPanelModel}、\texttt{RunMapState}）；
  \item \textbf{View}：Laya 预制体与 UI2 节点绑定，负责显示与布局；
  \item \textbf{Controller}：继承 \texttt{UiControllerBase}，处理生命周期、输入与路由，不直接操作战斗场景中的实体节点。
\end{itemize}

元游戏包含开始、选关、跑图等多个全屏界面。若允许多个面板同时 \texttt{visible}，易出现遮挡与事件穿透问题。本项目以 \texttt{UIStackManager} 维护路由栈：\texttt{push(routeId)} 入栈并显示对应 Controller，\texttt{pop()} 出栈恢复上一层，保证任意时刻仅一个全屏界面占据焦点。该模式与 Gregory 所述“将界面状态机与玩法逻辑解耦”一致\cite{gregory2018game}。

\subsection{战斗内 UI：HUD、暂停与技能装配}

局内 UI 包括主 HUD（血条、经验）、升级奖励面板、死亡重启面板与 \textbf{Tab 技能装配面板}。\texttt{SkillSelectPanelController} 监听 Tab：打开时将 \texttt{GameSession.paused} 置为真，战斗 System 在 \texttt{update} 入口早退，怪物与子弹逻辑冻结，但 UI 仍接收指针事件——即\textbf{输入层与战斗逻辑层分离}，避免“面板打开仍被怪物攻击”的体验问题。

技能装配采用长按拖拽：\texttt{SkillDragService} 在按下超过阈值后创建顶层代理图标，规避 \texttt{GBox} 裁剪导致的命中错误；\texttt{SkillSlotHitTest} 统一坐标系判断落点属于装备栏或效果槽。关闭面板时，\texttt{SkillLoadoutSyncSystem} 将 \texttt{SkillLoadoutState} 原子写回 \texttt{Skill} 组件与 \texttt{PlayerAutoCastSystem}，防止半状态导致仍施放旧技能。图标由配表 \texttt{iconPath} 与 \texttt{SkillIconBinder} 加载，资源目录约定文件名与 id 对应，减少冗余字段。

跑图界面 \texttt{RunMapPanelView} 根据 DAG 状态渲染节点与连线，\texttt{MapNodeIconUtil}、\texttt{LineLayoutUtil} 负责布局；玩家只能选择与当前节点相邻且已解锁的边，规则由模型层校验而非 View 硬编码。

\subsection{UI 架构选型的综合评价}

\section{本章小结}

本章围绕引擎语言、玩法架构、UI 架构三个维度，阐述了 LayaAir + TypeScript、轻量 ECS + 配表驱动 + Roguelite 跑图、MVC + UI 栈的技术路线及取舍依据，并修正了与毕业设计规模不匹配的过度工程化方案（如完整 DOTS）。后续第三、四章在此基础上展开需求分析与总体设计；第五、六章则对应具体实现与性能优化。全文引用游戏引擎架构、人群仿真与软件可维护性等领域文献\cite{ullmann2025sydra,gregory2018game,cantrell2018unity,heijstek2011empirical}，以支撑选型论述的规范性。
