\chapter{系统总体设计}
\label{chap:architecture}

\section{设计原则}

系统总体设计遵循以下原则，并在后续模块实现中反复体现：

\begin{enumerate}[label=(\arabic*)]
  \item \textbf{数据与逻辑分离}：组件仅存数据，系统执逻辑；可调参数尽量外置 JSON 配表，工程常量集中于 \texttt{src/defines/}\cite{gregory2018game}。
  \item \textbf{单一职责}：\texttt{BulletSystem} 负责子弹运动与碰撞；\texttt{EffectExecutor} 负责配表效果解释；\texttt{MetaFlowController} 仅协调元游戏流程，不直接改写 ECS 组件\cite{briand2001maintainability}。
  \item \textbf{可验证}：核心模块提供公式解析、ECS 核心、属性修饰器等单元验证脚本，变更后可快速回归\cite{petty2010vv}。
  \item \textbf{渐进复杂度}：先做轻量 ECS 和单线程 tick；池化和 Worker 只在怪够多时再开。
  \item \textbf{低耦合}：UI 经 Controller、SyncSystem 读写 ECS；Worker 与主线程共用一份 \texttt{combatWorkerLogic.ts}\cite{ullmann2023coupling}。
  \item \textbf{可降级}：表没加载、Worker 起不来、地图生成失败时，都有回退（第~\ref{sec:reliability}~节、第~\ref{sec:fault-tolerance}~节）。
\end{enumerate}

\subsection{基于 ECS 的 Gameplay 实现}
\label{sec:ecs-design}

局内玩法走 ECS。\texttt{EntityId} 是数字；\texttt{ComponentStore} 用 \texttt{Map} 按类型存组件；\texttt{EcsWorld} 按 \texttt{input/logic/render} 分组调 System。\texttt{Position}、\texttt{Velocity}、\texttt{Attribute}、\texttt{Skill} 等只放数据；\texttt{MovementSystem}、\texttt{BulletSystem} 等遍历实体改字段，本身不记状态。

\textbf{标签与筛选}：玩家与怪物共享位移、属性、技能等组件，仅通过 \texttt{PlayerTag}/\texttt{MonsterTag} 区分。\texttt{FilterRegistry} 提供 \texttt{Players}、\texttt{Monsters} 等命名筛选器，避免各 System 重复编写交集查询。该设计体现\textbf{组合优于继承}：新增怪物行为时扩展组件字段或新增 System，而非维护 \texttt{MonsterBase} 类树。

\textbf{战斗数据流}：每帧 \texttt{CombatDataPrepareSystem} 采集坐标等快照 $\rightarrow$ 可选 \texttt{CombatDataBridge} 提交 Worker 执行 \texttt{processCombatFrame} $\rightarrow$ 主线程 \texttt{MonsterChaseSystem} 应用追逐/分离结果 $\rightarrow$ \texttt{BulletSystem} 在主线程完成碰撞（依赖 Laya 节点与阵营判定）。\texttt{GameSession.paused} 在死亡、技能 Tab 或胜利时冻结逻辑 System 的 \texttt{update} 入口。

\textbf{配表驱动}：\texttt{Skill} 与多行 \texttt{SkillEffect} 描述冷却与效果链；\texttt{EffectExecutor} 按序解释 \texttt{bullet}、\texttt{modifier\_*}、\texttt{direct\_damage}。修饰器须位于后续 \texttt{bullet} 之前，形成链式组合语义。伤害字符串由 \texttt{FormulaParser} 在白名单运算下解析，禁止 \texttt{eval}。

\subsection{基于 MVC 的 UI 结构实现}
\label{sec:mvc-design}

元游戏与局内 UI 采用 \textbf{MVC 变体}\cite{heijstek2011empirical}：
\begin{itemize}
  \item \textbf{Model}：hp、装配来自 ECS；跑图用 \texttt{RunMapPanelModel}、\texttt{RunMapState}；
  \item \textbf{View}：预制体、UI2 节点负责布局；
  \item \textbf{Controller}：\texttt{UiControllerBase} 子类管生命周期和路由，\textbf{不得}直接改战斗实体。
\end{itemize}

全屏页走 \texttt{UIStackManager}：\texttt{push} 显示、\texttt{pop} 返回，始终只有一个全屏页在前台。\texttt{MetaMenuBootstrap} 注册开始、选关、跑图路由。

局内 Tab 由 \texttt{SkillSelectPanelController} 监听：打开时 \texttt{GameSession.paused=true}，战斗 System 不 tick，UI 仍能吃点击。拖拽走 \texttt{SkillDragService}，落点用 \texttt{SkillSlotHitTest}；关面板时 \texttt{SkillLoadoutSyncSystem} 一次性写回 \texttt{Skill} 和 \texttt{PlayerAutoCastSystem}。跑图连线由 \texttt{RunMapPanelView} 画，能不能走由 Model 判，View 不写规则。

核心约束：\textbf{界面不拥有玩法真相}——玩法状态以 ECS 与配表为准，UI 仅经 Controller/SyncSystem 读写。

\subsection{基于 Web Worker 和对象池的优化实现}
\label{sec:perf-design}

\textbf{对象池}：\texttt{BulletPool}、\texttt{MonsterPool} 按预制体路径分桶复用 Laya 节点，抑制 \texttt{instantiate/destroy} 触发的 GC 尖峰。\texttt{MonsterRecycleSystem} 在怪物远离玩家超过阈值后回收实体，维持活跃集合规模。

\textbf{Web Worker}：当场上实体数 $\geq$ \texttt{COMBAT\_WORKER\_MIN\_ENTITY\_COUNT} 时，\texttt{CombatDataPrepareSystem} 将快照经 \texttt{CombatDataBridge} 发送至 Worker；\texttt{combatWorkerLogic.ts} 在主线程与 Worker 间共享，计算追逐、分离与摆动。\texttt{CombatDataBridge.prepareFrame} 优先消费异步结果，失败或未就绪时调用 \texttt{computeSync} 回退。子弹碰撞、连锁与分裂仍保留主线程，因依赖引擎节点与即时命中判定。

\textbf{逻辑暂停}：\texttt{GameSession.paused} 在技能面板、死亡、胜利时让战斗 System 直接 return，不额外分配资源，思路与 Cantrell 等把重算和画面拆开一致\cite{cantrell2018unity}。

\section{可靠性设计}
\label{sec:reliability}

配表坏了、Worker 起不来、地图生成失败时，系统应尽量还能玩或至少能调试，而不是白屏退出。做法如下。

\textbf{（1）配表加载与就绪判据}。\texttt{ConfigBootstrap.ensureGameConfigLoaded} 遍历 \texttt{configBases()}，依次尝试 \texttt{fetch} 与 \texttt{Laya.loader} 双通道加载 \texttt{tables.registry.json} 及各表；\texttt{isGameConfigReady()} 要求 \texttt{configLoaded} 且 \texttt{Data.Skill} 非空，作为“可否进入战斗”的全局闸门。\texttt{Main.onStart} 与 \texttt{SimpleEcsDemo.spawnPlayer} 均在生成实体前等待或复查该状态。

\textbf{（2）运行时缺表降级}。\texttt{SimpleEcsDemo} 维护 \texttt{missingConfigLogged: Set<string>}，通过 \texttt{logMissingConfigOnce} 对每个缺失键仅告警一次，避免刷屏。\texttt{defines} 中 \texttt{DEFAULT\_PLAYER\_HP}、\texttt{DEFAULT\_PLAYER\_PREFAB}、\texttt{DEFAULT\_PLAYER\_AUTO\_SKILL\_ID} 等在查表失败时回退；升级奖池表为空时返回内联默认条目，保证演示不中断。

\textbf{（3）Worker 双路径}。\texttt{CombatDataBridge.initWorker} 失败、\texttt{onerror} 或 \texttt{postMessage} 异常时将 \texttt{workerUsable=false}；\texttt{prepareFrame} 无可用异步结果时调用 \texttt{computeSync}，与 Worker 共用 \texttt{processCombatFrame}。\texttt{MonsterChaseSystem} 无 Worker 结果时走本地追逐+分离；\texttt{BulletSystem} 在存在连锁弹等 Worker 未覆盖场景时回退完整主线程逻辑。实体数低于 \texttt{COMBAT\_WORKER\_MIN\_ENTITY\_COUNT} 时不提交 Worker，减少通信开销。

\textbf{（4）跑图生成保底}。\texttt{RunMapGenerator.generate} 在最多 \texttt{RUN\_MAP\_GENERATION\_MAX\_RETRIES} 次随机尝试后，若 \texttt{validateActReachBoss} 仍失败，则调用 \texttt{generateFallback} 生成三幕各「休息$\rightarrow$战斗$\rightarrow$Boss」线性图，保证 Boss 可达、进度不卡死。

\textbf{（5）重启防重入}。\texttt{RestartPanelSystem} 将 \texttt{session.restartRequested} 置真；\texttt{SimpleEcsDemo.tryRestartFromSession} 在 \texttt{restarting=true} 期间异步清场与重生，\texttt{update} 中避免重复触发，\texttt{finally} 复位标志，防止监听器与实体重复注册。

\textbf{（6）预制体加载失败}。实例化失败时 \texttt{createPlaceholderNode()} 生成占位碰撞体，便于在无美术资源环境下继续调试逻辑。

\section{可扩展性设计}
\label{sec:extensibility}

本系统的可扩展性建立在 ECS 的\textbf{组合优于继承}原则之上，而非为每种怪物或技能派生子类。

\textbf{实体扩展}：新玩法维度优先\textbf{新增组件类型}（如未来的 \texttt{BuffComponent}、\texttt{ShieldComponent}），再在独立 System 中读写；已有 \texttt{MonsterTag} 实体自动参与 \texttt{FilterRegistry.Monsters}，无需修改 \texttt{EcsWorld} 内核。

\textbf{行为扩展}：新行为对应新 System 或扩展现有 System 的分支；例如新增“光环”只需注册 \texttt{AuraSystem} 并在 \texttt{SimpleEcsDemo} 构造函数中 \texttt{addSystem}，不必改动 \texttt{MovementSystem}。

\textbf{技能扩展}：新 \texttt{effect} 类型在 \texttt{EffectExecutor} 增加分支；修饰器仍通过“写上下文 $\rightarrow$ 后续 bullet 消费”扩展，策划在 \texttt{SkillEffect} 表调序即可组合。新子弹形态仅需配表 \texttt{Bullet} 行与预制体路径。

\textbf{内容扩展}：新跑图节点类型扩展 \texttt{RunNodeType} 与 \texttt{RunMapGenerator} 权重表；新全屏界面在 \texttt{UIStackManager} 注册路由与 Controller，不修改战斗 ECS。

\textbf{与继承方案对比}：若采用 \texttt{Player extends Character extends Actor}，每增加一种“会分裂的精英怪”都需新建子类并重写 \texttt{update}，导致 Laya 节点与逻辑深度耦合。当前方案下，精英怪仅是 \texttt{MonsterTag} + 额外组件（如更高 \texttt{Attribute} 或专用 \texttt{MonsterDef.waveWeight}），行为差异由 \texttt{MonsterAutoCastSystem} 等组合完成，符合 Gregory 与 ECS 文献对“数据导向、增量扩展”的论述\cite{gregory2018game}。

\section{本章小结}

本章给出设计原则、分层架构，并从 ECS Gameplay、MVC UI、Worker/对象池三方面说明系统具体设计；进一步给出端到端时序、可靠性机制、容错表与基于组合的可扩展性策略，为第~\ref{chap:modules}~章实现细节提供结构框架。
