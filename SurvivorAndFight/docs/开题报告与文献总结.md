# 开题报告

## 1 选题目的及研究意义

### 1.1 选题背景与问题提出

近年来，以《Vampire Survivors》（吸血鬼幸存者）为代表的类幸存者游戏在独立游戏与移动端市场持续升温。该类游戏具有“单局时长短、局内成长可见、弹幕密集、重玩价值高”等鲜明特点，对游戏架构提出了明确要求：同屏需支撑数千计的怪物与弹幕实体、角色成长与技能选择需可配置可扩展、战斗与关卡逻辑需清晰分层以便迭代。传统以面向对象、单一大类继承为主的游戏架构，在实体数量急剧增多时容易暴露出逻辑与表现耦合、扩展成本高、CPU 缓存命中率低等问题，难以在 Web 端稳定维持 60Fps 的高性能表现。[1]

图1-1 传统游戏架构在类幸存者游戏场景下面临的主要问题

- **对开发效率而言**：逻辑与表现耦合紧密，新增一种怪物或技能往往需要修改多处代码，迭代成本高、回归风险大。
- **对扩展性而言**：难以在不改动核心逻辑的前提下，仅通过配置（如配表）增加新角色、新怪物、新弹幕与技能效果，不利于内容迭代与多版本复用。
- **对性能而言**：缺乏数据与逻辑的分离，同屏实体增多时难以做到缓存友好的连续内存访问与批量处理，无法充分发挥现代 CPU 与多线程能力。

### 1.2 ECS 架构的价值与适用性

实体组件系统（Entity-Component-System, ECS）将“实体”抽象为仅含唯一标识的容器，将“行为”拆解为纯数据的“组件”与纯逻辑的“系统”，通过数据驱动更新，有利于数据局部性、逻辑解耦和配置驱动，已在工业与学术场景形成较成熟的方法体系。[1][4] 在 H5 与轻量级项目中，复刻 Unity DOTS 核心思想、设计轻量级 ECS 框架，既能保持结构清晰、便于毕设实现与教学演示，又可通过内存布局优化、多线程优化等手段，为同屏数千实体、Web 端 60Fps 稳定运行提供技术基础。

### 1.3 国产引擎与 H5 技术栈的意义

LayaAir 作为国产 H5/跨平台游戏引擎，在 2D/3D 渲染、资源管线、TypeScript 支持及多端发布方面已较为成熟，适合作为“从引擎到玩法、从框架到优化”的一体化实践平台。将自研 ECS 框架与 LayaAir 深度结合，实现实体与 Laya GameObject 的自动关联与同步，并配套视锥体裁剪、LOD、对象池等性能优化套件以及性能分析工具链，有助于为 H5 游戏开发提供高性能、可复用的解决方案，对构建更专业、可复用的国产游戏开发技术栈具有实际意义。[1][4]

### 1.4 本课题的研究目的与意义归纳

本课题旨在基于 LayaAir 引擎，设计并实现一套面向类吸血鬼幸存者玩法的 ECS 架构框架及完整游戏实例，并围绕大规模实体管理、多线程与内存优化、开发工具链等方面进行系统化研究与实现。具体包括：复刻 Unity DOTS 核心思想的轻量级 ECS 核心、实体与 Laya 游戏对象自动绑定系统、支持 TagComponent/DataComponent/ShareComponent 等的组件系统设计；实现同屏数千怪物与弹幕的流畅运行（目标 Web 端 60Fps 稳定）、角色成长系统、怪物生成与 AI（基于 ECS 的行为树）、装备与道具、技能与战斗（大量弹幕效果）、关卡与进度（随机地图、波次管理、Boss 战）；并配套视锥体裁剪、LOD、对象池等性能优化套件以及帧率监控、内存分析等开发工具。通过上述工作，全面提升游戏开发的效率与性能表现，并为国产 H5 游戏技术栈的规范化与复用提供参考。

## 2 国内外研究现状

### 2.1 ECS 架构与数据导向设计研究现状

游戏引擎架构从早期单线程、面向对象设计，逐步演进到数据导向（Data-Oriented）、组件化与多线程协同。ECS 将“实体”抽象为 ID 容器，将“组件”限定为数据，将“系统”限定为处理逻辑，可显著改善逻辑耦合、迭代修改成本与数据访问局部性。[1][2]

在 Unity 生态中，相关研究与工程实践表明：当项目进入高频迭代阶段时，传统继承树结构容易出现跨模块牵连修改，而 ECS 在“功能组合而非继承扩展”方面具备更好的可维护性；同时，围绕事件系统、依赖注入、编辑器可用性与序列化能力的工程化补充，决定了 ECS 是否能在真实项目中落地。[1] 这类经验对本课题“轻量 ECS + H5 引擎集成”的方向具有直接参考价值。

从架构恢复与可维护性视角看，最新研究提出了 SyDRA（Subsystem-Dependency Recovery Approach）用于理解游戏引擎架构耦合关系。该研究通过对 10 个开源游戏引擎的子系统依赖图分析与对照实验，证明“结构可视化模型”可显著提升开发者在架构理解与影响分析任务中的正确率与效率。[2] 这为本课题后续进行 ECS 模块边界划分、依赖治理与演化评估提供了方法论支撑。

### 2.2 游戏引擎与 H5 跨平台技术研究现状

LayaAir、Cocos 等国产引擎在 H5、小程序与多端发布领域应用广泛。LayaAir 3.x 支持 TypeScript 与 2D/3D 混合开发，适合进行“引擎层能力 + 玩法层架构”一体化实践。在 H5 场景中，性能瓶颈通常集中于实体规模、渲染批次、频繁创建销毁导致的 GC 抖动与逻辑层查询成本，因此需要采用对象池、可见性裁剪、LOD 与数据驱动更新等组合策略。[1][2]

此外，SyDRA 对引擎子系统耦合模式（如 Core、Renderer、Resources 高频耦合）给出的实证结果提示：在架构演进中，若缺乏清晰边界与依赖治理，后续功能叠加会显著增加维护成本。[2] 该结论与本课题“先定能力边界，再逐步扩展玩法系统”的技术路线一致。

### 2.3 类吸血鬼幸存者游戏与 Roguelike 玩法研究现状

类吸血鬼幸存者游戏源自《Vampire Survivors》等作品，核心特征包括：俯视角、自动或半自动攻击/技能、大量敌怪与弹幕、局内成长与装备选择、单局时长约 10–30 分钟。其玩法对“大规模实体管理、碰撞检测、技能与数值配置、波次与关卡生成、UI 反馈”等模块有明确需求。[5] 国内外对 Roguelike 与类幸存者游戏的设计分析多从玩法设计、数值曲线与关卡设计角度展开；从软件工程与架构角度，强调 ECS、配表驱动、行为树与性能优化相结合的系统性文献相对分散，本课题结合具体框架开发与游戏实例，可对上述方向进行归纳与验证。[1][5]

### 2.4 性能优化与开发工具链研究现状

在游戏性能优化方面，视锥体裁剪、空间划分（如四叉树/八叉树）、LOD（Level of Detail）、对象池、批处理与多线程调度已成为主流手段；在 ECS 场景下，通过连续内存布局、组件批处理与查询约束，可进一步提升缓存命中与可预测性。[1]

在验证与分析方法方面，Cantrell 等使用 Unity 构建人群疏散物理模型，并通过 The Station nightclub 实际事件进行定量校验，给出了“模型构建—功能测试—参数标定—置信区间验证”的完整评估链路。[3] 该研究对本课题具有两点启示：其一，游戏引擎可用于严肃的高并发动态系统建模；其二，性能与行为正确性应通过可重复实验与统计指标共同验证，而不仅依赖主观体验。基于此，本课题将性能工具链与实验设计纳入同一研究闭环。

## 3 相关技术原理及技术路线

### 3.1 ECS 核心框架原理

本项目采用“复刻 Unity DOTS 核心思想”的轻量级 ECS 框架，在保证结构清晰与可扩展性的基础上，逐步引入内存布局优化与多线程扩展点。

- **实体（Entity）**：使用数字类型 EntityId 作为唯一标识，由 EntityManager 负责创建、销毁及复用，并维护实体所拥有的组件类型集合，为后续按组件组合查询与内存分块预留接口。
- **组件（Component）**：强调“只存数据、不含游戏逻辑”。支持多种组件类型设计：
  - **TagComponent**：仅作标记，无或极少数据，用于实体分类与筛选（如 PlayerTag、MonsterTag）。
  - **DataComponent**：承载业务数据，如 Position、Velocity、Attribute、Skill 等，按 EntityId 索引存储。
  - **ShareComponent**（可选）：可在多实体间共享的只读或共享数据，用于减少冗余与提高缓存效率。
- **系统（System）**：具有统一接口（如 `update(deltaTime: number)`），按“分组 + 优先级”顺序执行（如：输入 → 逻辑 → 物理/碰撞 → 视图同步），在 Laya 主循环中挂接统一入口（如 `EcsWorld.update(deltaTime)`）。
- **内存布局优化**：采用连续内存存储同类型组件，提高 CPU 缓存命中率；在设计与接口上预留从“按类型 Map/数组”向 Archetype/Chunk 布局演进的空间，便于后续性能攻坚。

### 3.2 实体与 Laya 游戏对象自动绑定系统

- **绑定关系**：通过 ViewComponent 或等价组件在 ECS 侧记录 Laya 场景节点（GameObject/Sprite3D 等）引用，建立 Entity 与 Laya 游戏对象的一一对应。
- **同步方向与顺序**：以 ECS 为逻辑权威，每帧先完成 ECS 侧移动、技能、碰撞等更新，再由 ViewSyncSystem 将 Position/Rotation 等同步到 Laya Transform，保证表现与数据一致；血条等 UI 通过 Body 预制体与 ProgressBar 绑定，由专门系统根据 Attribute 的 hp/maxHp 等同步进度值。
- **生命周期**：实体创建时根据配表实例化 Laya 预制体并写入 View 组件；实体销毁时回收节点或归还对象池，避免泄漏与抖动。

### 3.3 类吸血鬼幸存者游戏实例涉及的系统

在 ECS 核心与实体–Laya 绑定之上，玩法层包含以下主要系统（与任务书对应）：

- **大规模实体管理**：通过对象池复用实体与组件，结合视锥体裁剪与空间划分，将同屏实体数量提升至数千量级，目标 Web 端 60Fps 稳定。
- **角色成长系统**：升级、经验与等级，以及升级时的技能选择（三选一或类似机制），用组件与系统表达，数据可配表。
- **怪物生成与 AI 系统**：波次与刷怪规则、生成位置与数量；怪物 AI 采用基于 ECS 的行为树或状态机，便于扩展与批量更新。
- **装备与道具系统**：装备槽位、属性加成与 Modifier 机制，与现有 Attribute 组件对接；道具拾取与效果通过组件与系统实现。
- **技能与战斗系统**：技能由多 effect 组成，支持自动/手动释放；大量弹幕效果通过子弹实体池与碰撞阵营规则实现，伤害与公式可配表。
- **关卡与进度系统**：随机地图生成（房间/地形/障碍）、波次管理、Boss 战触发与机制，通过关卡组件与专门系统驱动。

### 3.4 战斗等级与随机升级系统

本课题设计并实现一套完整的战斗等级与随机升级系统，为玩家提供可持续的战斗成长循环。该系统的核心设计如下：

#### 3.4.1 战斗等级系统

- **经验获取机制**：玩家通过击杀怪物获得经验值，经验值达到预设阈值后触发升级。
- **多级经验曲线**：支持配置化的经验曲线，可根据游戏进度调整升级难度与节奏。
- **等级属性提升**：每次升级可为玩家带来基础属性提升，形成稳定的数值成长路径。

#### 3.4.2 随机升级能力系统

- **升级候选项生成**：每次升级时从候选池中随机抽取若干选项（默认为3选1），供玩家选择。
- **权重与约束机制**：支持配置选项出现权重、前置条件（如已有某子弹类型才能选择对应增强）、重复上限与互斥约束。
- **升级效果类型**：
  - 获取新的子弹类型（散射弹、分裂弹、回旋弹等可扩展类型）
  - 增加每次发射子弹数量（Multi-shot）
  - 增加子弹穿透次数（Penetration）
  - 提升子弹基础数值（伤害、速度、持续时间、发射间隔等）

#### 3.4.3 战斗成长配置化

- 将战斗成长关键参数从业务逻辑抽离到配表与静态定义文件（Define），包括：
  - 等级经验阈值表（level_table.json）
  - 升级候选池配置（upgrade_pool_table.json）
  - 升级效果参数表（upgrade_effect_table.json）
- 通过配表驱动实现“零代码扩展”新子弹类型与新升级效果。

#### 3.4.4 升级交互流程

- **战斗暂停**：升级触发时暂停游戏逻辑，弹出升级选择面板。
- **候选项展示**：以卡片或按钮形式展示3个候选选项，显示效果名称、图标与描述。
- **确认生效**：玩家选择后应用升级效果，恢复战斗。
- **反馈特效**：可选播放确认特效增强获得感。

### 3.5 MVC UI 栈式系统与红点树池化机制

本课题设计并实现一套统一的 UI 架构，支撑多界面切换、红点通知与对象复用。

#### 3.5.1 MVC UI 生命周期管理

- **Model（数据层）**：负责界面数据的加载、存储与管理，与 ECS 组件系统对接，实现数据驱动 UI 更新。
- **View（表现层）**：负责界面渲染与用户输入响应，基于 LayaAir UI 组件构建。
- **Controller（控制层）**：负责业务逻辑处理、界面跳转控制与事件分发，协调 Model 与 View 的交互。
- **生命周期阶段**：定义完整的界面生命周期（创建、显示、隐藏、销毁），确保资源正确加载与释放。

#### 3.5.2 UI 栈式管理系统

- **栈结构管理**：维护界面栈的入栈、出栈顺序，支持多级界面嵌套。
- **遮罩与模态**：支持遮罩层管理，确保模态界面的正确弹出与关闭顺序。
- **返回与导航**：支持系统返回键与界面导航，处理界面回退逻辑。
- **并发控制**：约束同时存在的界面数量与类型，避免界面冲突。

#### 3.5.3 红点树系统

- **树形节点结构**：以树形结构组织红点节点，支持多级父子关系。
- **聚合计算规则**：子节点红点状态向上聚合，父节点根据子节点状态自动计算显示逻辑。
- **事件驱动更新**：红点状态变化时通过事件机制通知相关界面，实现实时响应。
- **界面解绑机制**：界面销毁时自动解除红点绑定，避免内存泄漏与无效通知。

#### 3.5.4 UI 对象池化

- **自动池化策略**：对常用 UI 组件（按钮、列表项、弹窗等）实施对象池化管理。
- **复用与清理**：复用池化对象时自动重置状态，界面销毁时归还对象到池中。
- **生命周期联动**：对象池与界面生命周期深度联动，确保资源高效利用。

### 3.6 性能优化套件原理

- **视锥体裁剪**：基于相机视锥体与 ECS 空间划分（如网格或树结构），快速剔除不可见实体，减少渲染与逻辑更新对象数量。
- **LOD（Level of Detail）**：根据实体与相机距离动态调整渲染精度（如模型复杂度、粒子数量、是否播放复杂动画），在保证观感的前提下降低绘制与动画开销。
- **内存与对象池**：对实体、子弹、怪物、特效等高频创建/销毁对象采用对象池，减少 GC 压力与分配抖动；组件与节点的回收与复用规则在框架层统一约定。

### 3.7 开发工具链

- **性能分析工具**：帧率监控与 FPS 曲线、每帧耗时分布；内存使用分析（如实体数、组件数、池容量等），便于定位瓶颈与验证优化效果。
- **与 ECS 的衔接**：工具可读取 World/EntityManager 的统计信息，或在开发模式下挂接调试用 System，输出关键指标到界面或日志。

### 3.8 技术路线总览

本项目基于 **LayaAir + TypeScript + 自研 ECS 框架 + JSON 配表 + 性能优化套件 + 开发工具链** 的技术栈，采用单机 H5 架构。整体架构如表 3-1 所示。

| 性能优化       | 视锥体裁剪、LOD、对象池、内存布局优化                         | 同屏数千实体、Web 端 60Fps 稳定 |
| 配置与数据     | JSON 配表、TableLoader、TablesRegistry                        | 角色、子弹、技能/效果、关卡等配表驱动 |
| 开发工具链     | 帧率监控与性能图表、内存使用分析                              | 性能瓶颈定位与优化验证 |

## 4 研究难点及目前存在的问题

### 4.1 研究难点

**4.1.1 ECS 与 LayaAir 的协同与数据流**

- 更新顺序必须严格约定：ECS 逻辑（移动、技能、碰撞、成长等）先执行，再同步到 Laya Transform 与 UI，否则易出现表现与数据不一致或“拖影”现象。
- 实体与 Laya 节点绑定需在“易用性”与“解耦”之间权衡：当前可采用组件内持节点引用或 RenderHandle 抽象，生命周期与池化回收需与 Laya 节点管理对齐，避免泄漏与重复绑定。

**4.1.2 大规模实体下的性能与多线程**

- 同屏数千实体时，单线程顺序更新可能成为瓶颈；需在内存布局（连续存储、Archetype/Chunk）与系统划分上为多线程或 Job 调度预留扩展点，同时兼顾 H5/Web Worker 的兼容性与调试成本。
- 对象池与组件复用时，须保证组件状态完全重置、无“脏数据”残留，否则会导致难以排查的逻辑错误。

**4.1.3 技能、公式与索敌的可配置性与正确性**

- 公式解析需统一属性别名与配表列名，采用白名单与默认值，避免运行时解析失败或注入风险。
- 索敌（如 auto 目标）的“威胁度”需与怪物 AI、仇恨或距离等挂钩，权重与参数需可配置且与文档一致。
- 技能表与 effect 表需同时支持多 effect、多目标类型、子弹/特效栏位等扩展，表结构设计需兼顾可读性与扩展性。

**4.1.4 行为树与怪物 AI 在 ECS 下的实现**

- 基于 ECS 的行为树要求节点与组件化数据结合，状态与黑板数据需与实体/组件对应，避免全局状态破坏 ECS 的数据局部性；行为树执行顺序与系统更新顺序也需协调，以便与移动、技能、碰撞等系统正确交互。

**4.1.5 战斗升级系统的配置化与平衡性**

- 升级候选项的权重、前置条件与互斥约束需要在配表中清晰定义，表结构设计需兼顾可扩展性与解析效率。
- 子弹类型（散射、分裂、回旋等）的多样化实现需要与现有子弹系统兼容，同时保证性能。
- 随机升级的数值平衡需要通过大量测试验证，确保不同build策略都有可持续的战斗体验。

**4.1.6 MVC UI 系统与 ECS 的数据对接**

- UI 的 Model 层需要高效读取 ECS 组件数据，需设计统一的数据订阅与更新机制。
- 红点树的聚合计算逻辑需与游戏进度系统对齐，确保状态准确。
- 对象池化需要与 LayaAir 的 UI 组件生命周期兼容，避免渲染异常。

### 4.2 目前存在的问题

- **性能与规模**：当前若为单线程、简单按类型存储组件，实体规模在几十到几百量级尚可；要达到同屏数千、60Fps 稳定，必须系统化地引入视锥体裁剪、LOD、对象池及可选的内存布局与多线程优化，工作量和难度均较高。
- **资源与加载**：大量预制体与配表的加载可能带来首包或场景切换卡顿，需通过异步加载、分帧实例化与池化策略缓解。
- **碰撞与阵营**：玩家子弹仅对怪物生效、怪物子弹仅对玩家生效等规则依赖碰撞体与阵营配置正确，配表与预制体命名、层级需统一约定，否则易出现误伤或无效碰撞。
- **工具链成熟度**：性能分析工具从零开发时，需与 ECS 的 World/Entity 统计、Laya 的渲染与 GC 信息对接，数据采集与展示的粒度需要迭代确定。
- **战斗深度**：现有战斗系统缺少可持续成长循环，需要通过升级系统补齐内容深度与重玩价值。
- **UI 架构**：需要统一不同界面的生命周期管理、红点通知机制与资源复用策略。

### 4.3 拟采取的措施

- 在设计与规范文档中明确“更新顺序、公式白名单、索敌权重、Modifier 合并顺序”等，并在代码中单点实现，避免多处分散逻辑导致不一致。
- 对子弹、怪物、特效等高频对象统一使用对象池，制定统一的“取出—使用—归还—重置”流程，并在关键路径上做简单性能 profiling，验证池化与裁剪效果。
- 行为树采用轻量实现，先支持顺序、选择、条件等基础节点，黑板数据与实体组件一一对应，便于调试与扩展。
- 性能工具先实现帧率与基础内存统计，再根据实际瓶颈增加实体数、系统耗时等维度，与 ECS 的查询接口对接，形成可复用的分析套件。
- 战斗升级系统采用配表驱动设计，预留充足的可配置参数，通过测试迭代调整数值平衡。
- UI 系统先实现基础栈式管理与界面基类，再逐步完善红点树与对象池化能力。
- 工程管理上采用规范驱动：每个阶段能力先定义需求规格，再实施与验证，确保需求边界、接口约定与验收标准一致，降低中后期返工风险。

# 文献总结

## 1 ECS 与数据导向设计

实体组件系统（ECS）将游戏对象拆分为实体（ID）、组件（数据）与系统（逻辑），强调数据局部性与逻辑解耦。Unity DOTS、Unreal Mass Entity 等工业方案采用 Archetype 与 Chunk 内存布局、Job 调度以提升缓存利用与多核并行；在轻量级与教学场景中，简化版 ECS（单线程、按类型存储）在保持可读性与可扩展性方面仍有广泛应用。相关研究涉及 ECS 的演进历史、与 OOP 的对比、内存布局对缓存命中率的影响以及多线程下的数据竞争与调度策略。[1][4][5]

## 2 游戏引擎与 H5 技术

LayaAir 作为国产 H5 游戏引擎，支持 2D/3D、TypeScript、WebGL2/WebGPU 与多端发布，适用于中小型游戏与教育项目。将引擎主循环与自研 ECS 的 update 挂接、将 ECS 的 Position 与 Laya Transform 同步，是实现“引擎+自研架构”的常见方式。H5 场景下的性能限制、包体与加载策略、与原生引擎的差异也是相关文献与工程实践的常见主题。[1][4]

## 3 类吸血鬼幸存者游戏与 Roguelike 设计

类吸血鬼幸存者游戏以大量同屏实体、自动/半自动战斗、局内成长与短局时长为主要特征，对实体管理、碰撞、技能与数值配置、波次与关卡、UI 反馈等模块要求明确。通过配表驱动角色、子弹与技能，可降低迭代成本并提高可维护性。Roguelike 与类幸存者游戏的玩法设计、数值曲线、关卡生成与难度平衡等在游戏设计领域有较多讨论。[5]

## 4 性能优化与工具链

视锥体裁剪、空间划分、LOD、对象池、批处理与多线程调度等是游戏性能优化的常用手段；在 ECS 语境下，连续内存、Archetype 分块与 Job 并行可进一步提高效率。帧率监控、性能图表与内存分析等工具对定位瓶颈、验证优化效果不可或缺；将这类工具与 ECS 的统计接口结合，可形成面向 H5 与 ECS 的专用分析套件。[1][3]

## 5 战斗系统与成长机制

类吸血鬼幸存者游戏的核心乐趣之一在于局内成长循环。通过击杀怪物获得经验、升级时提供随机选项（3选1或其他形式）、选择后将成长效果（获取新技能、提升属性、强化武器等）永久化或阶段性强化，是该品类经典的成长范式。相关设计涉及经验曲线数值配置、随机池权重算法、条件互斥逻辑、UI 交互流程等多个维度，需与 ECS 架构和配表系统深度结合以实现可扩展性。[5]

## 6 UI 架构与设计模式

现代游戏 UI 系统普遍采用 MVC 或 MVP 等设计模式实现关注点分离；界面栈式管理用于处理多级界面切换与返回逻辑；红点系统作为通知与引导机制广泛存在于移动游戏中；对象池化技术应用于 UI 组件的复用以降低内存波动。将这些模式与 H5 引擎、Layabox UI 组件结合，需针对 Web 端特点进行适配与优化。
