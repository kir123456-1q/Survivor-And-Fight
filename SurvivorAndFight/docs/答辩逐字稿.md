## 第 2 页｜研究背景与意义（约 1.5 分钟）

首先介绍研究背景与意义。

H5 游戏链接即玩，但浏览器 JavaScript 往往只有一条主线程，GC 和绘制共用每帧时间。类吸血鬼幸存者玩法同屏怪物和弹幕数量大，若在单帧里堆太多位移、碰撞和界面刷新，帧率很容易掉。

同时，这类游戏常叠加 Roguelite 元游戏：菜单、选关、跑图、战斗要串成完整闭环，客户端需要在数据驱动、模块划分和可测性上划清边界。

针对这些痛点，本课题从四个方向入手：

第一，采用轻量 ECS 架构，验证实体组件系统在 H5 生存战斗中的落地效果，解耦数据与表现。

第二，建设配表技能系统，用数据驱动实现技能配置化，提升可测性和迭代效率。

第三，用对象池与 Web Worker，解决高同屏实体下的帧率卡顿，把计算密集型任务移出主线程。

第四，以 Survivor And Fight 为对象，在 LayaAir 3.x 与 TypeScript 上完成可演示、可测的原型。

---

## 第 3 页｜技术选型（约 1 分钟）

接下来是技术选型。

引擎选用 LayaAir 3.x，原因是 IDE 一体、TypeScript 原生、2D 与 UI2 组件完备，符合 H5 游戏开发需求。

语言选用 TypeScript，利用静态类型检查，让模块划分更清晰，降低维护成本。

玩法架构采用轻量 ECS，组合优于继承，便于批量处理实体，支撑数百同屏实体规模。

UI 采用 MVC 变体，把界面与战斗逻辑解耦，便于迭代。

性能优化采用对象池加 Web Worker，抑制 GC 尖峰，卸载纯数值计算。

这里需要说明：商业引擎如 Unity DOTS 面向数万实体并行，而本项目采用教学向轻量 ECS——EntityId 为数值，ComponentStore 按组件类型用 Map 存储，EcsWorld.update 单线程顺序调用已注册系统。第一期目标是结构清晰、支撑数百同屏实体，不追求极致数据导向布局。

## 第 4 页｜总体架构设计（约 1.5 分钟）

系统按五层划分，上层只依赖下层。

**01 表现层**：负责 Laya 节点与 HUD 显示，不包含业务规则。

**02 UI 控制层**：包含 UIStackManager、各类页面 Controller，经 SyncSystem 读写 ECS。

**03 游戏逻辑层**：ECS 核心玩法，集中注册 System 和对象池，是性能优化的核心作用域。

**04 领域服务层**：包含配表加载、战斗入口等公共服务。

**05 基础设施层**：包含 EcsWorld、静态常量、对象池与 Worker 协议等基础能力。

设计原则有三点：数据与逻辑分离、单一职责，以及可验证、可降级——配表加载失败有回退，Worker 失败有主线程兜底。

---

## 第 5 页｜项目核心创新点（约 1 分钟）

本项目核心创新点可以概括为四个方面。

**第一，轻量 ECS 设计**：EcsWorld 驱动玩法 tick，ViewComponent 仅绑定 Laya 节点，业务不直接调用引擎 API，新增怪物行为只需增 System 或扩展组件字段，无需维护继承树。

**第二，多维度性能优化**：对象池、Web Worker、动态图集组合使用。千怪场景下，对象池使 P95 帧时间降低约 36.5%；动态图集使千怪波 FPS 提升约 13.4%。

**第三，UI 与战斗协同**：UIStackManager 管理全屏页面栈；打开技能装配面板时自动暂停战斗逻辑；同步机制保证装配修改原子生效。

**第四，数据驱动**：JSON 配表驱动技能效果，数值改动不必重新编译。

## 第 7 页｜ECS 三要素（约 40 秒）

ECS 在本项目中的定义如下：

**Entity** 仅为数值 ID，不包含逻辑与数据。

**Component** 是纯数据，只存字段，如 Position、Velocity、Attribute、Skill 等。

**System** 是无状态系统，遍历实体改字段，本身不记状态，如 MovementSystem、BulletSystem 等。

---

## 第 8 页｜ECS 实现细节（约 1.5 分钟）

实现层面，EntityManager 用自增 EntityId 加空闲列表复用；ComponentStore 按组件类型分 Map 存储，EntityId 为键。

玩家与怪物共用组件，靠 PlayerTag 或 MonsterTag 区分身份。FilterRegistry 预先注册 Players、Monsters 等筛选名，各 System 按名取实体，避免每帧全量遍历。

System 按 input、logic、physics、render 分组排序，同组内按 priority 从高到低执行。核心职责包括：MovementSystem 推进位移，AttributeSystem 重算属性，SkillSystem 与 BulletSystem 处理施法与子弹。

---

## 第 9 页｜配表技能 effect 链（约 1 分钟）

技能效果通过 JSON 配表驱动。effect 字段对应不同行为：bullet 调用 BulletSystem.spawnBulletWithOptions；modifier_split 设置分裂数量；modifier_chain 设置连锁与半径；modifier_pierce 增加穿透；direct_damage 走公式直伤。

执行顺序有约束：modifier 行只累加 pending 变量，bullet 行才把 pending 写入 BulletSpawnSpec 并真正生成子弹。因此 modifier 行必须排在对应 bullet 行之前。若策划把 modifier 放在 bullet 之后，pending 无法被消费，会出现「有修饰无弹幕」的配置错误。项目用 verify 脚本做回归检查。

---

## 第 10 页｜性能瓶颈分析（约 40 秒）

Level3 测试场景为 1920×1080，目标 60 FPS。五波加压测试暴露三类瓶颈：

**CPU 开销**：MonsterChaseSystem 与 BulletSystem，上千实体时追逐、圆碰撞、连锁搜索都会上去。

**GC 尖刺**：关掉 BulletPool、MonsterPool 后，spawn 路径频繁 instantiate 和 destroy，浏览器表现为 Scripting/GC 尖刺。

**渲染压力**：主线程还要跑 Laya 绘制和 UI，千怪千弹时 DrawCall 和贴图采样也会吃时间。

这三类瓶颈分别对应后续的 Worker、对象池和动态图集优化。

第二部分：**MVC 架构的定义、实现与验证**。

## 第 12 页｜MVC 职责划分（约 1 分钟）

MVC 在本项目中的职责如下：

**Model**：hp、装配状态等来自 ECS；跑图另有 RunMapPanelModel、RunMapState。

**View**：预制体和 UI2 节点只管摆位和显示，不写业务规则。

**Controller**：UiControllerBase 子类管生命周期和路由，不碰战斗场景里的实体节点。

关键原则是：玩法状态以 ECS 与配表为准，UI 仅经 Controller 或 SyncSystem 读写，System 不直接操作 UI 节点。

局内变体可概括为：ECS 组件为 Model，View 为预制体节点，Controller 与 System 负责输入与同步。

---

## 第 13 页｜UI 生命周期与栈管理（约 1 分钟）

Controller 生命周期为：Created → initialize → Initialized → show → Shown → hide → Hidden → dispose → Disposed。

show 时若 state 仍为 Created 会抛错，要求先 initialize。onInitialize、onShow、onHide、onDispose 均为子类必须实现的抽象方法。

UIStackManager 负责全屏页面栈：register 注册路由工厂，push 时隐藏栈顶、新建 Controller 并 initialize、show、入栈；pop 时 hide、dispose、恢复下一层 show。

操作经队列串行化，避免并发 push/pop 乱序；同一时刻只有一个全屏页处于 Shown，避免多面板叠层和事件冲突。

---

## 第 14 页｜跑图 Controller 示例（约 30 秒）

以 RunMapPanelController 为例：持有 model 与 view，onShow 时 model.applyPayload 应用参数，从 model.runMapState 取状态绑定到 view。view.setOnNodeClicked 监听节点点击，handleNodeClick 处理业务逻辑。View 只负责画和显隐，用 mapState 决定 alpha 和可点性，不写业务规则。

---

## 第 15 页｜Tab 技能装配协同（约 1.5 分钟）

Tab 技能装配是 UI 与战斗协同的典型场景，流程如下：

玩家按 Tab，SkillSelectPanelController 把 session.paused 设为 true，各 System 在 update 开头 return，怪物不再追、子弹不再出新。

面板打开期间，SkillDragService 代理拖拽，SkillSlotHitTest 判断落点是装备栏还是 effect 槽，改动先写入 SkillLoadoutState 临时对象，不直接改战斗实体。

关闭面板时，SkillLoadoutSyncSystem 把 loadout 一次性同步到 Skill 组件，并刷新 PlayerAutoCastSystem 的待施法列表，再把 paused 恢复为 false，下一周期 Cast 参与施放。

这样保证了：面板打开时战斗暂停、输入给 UI；关闭后装配原子生效、战斗恢复。

## 第 17 页｜Worker 设计原则（约 1 分钟）

Worker 不能碰 DOM 和多数引擎 API，碰撞和渲染必须留主线程。Worker 只适合搬纯数值计算，如追逐、邻域排斥、摆动等。

主线程与 Worker 共用 combatWorkerLogic.ts，避免两套算法各写一遍。

启用有阈值：场上实体数达到 COMBAT_WORKER_MIN_ENTITY_COUNT 后才启用；低于阈值不送数据，省掉序列化和 postMessage 成本。

子弹碰撞、连锁、分裂仍由主线程完成，须读取节点位置与阵营。

回退机制：initWorker 失败、Worker onerror 或 postMessage 抛错时，workerUsable 设为 false，prepareFrame 拿不到异步结果就走 computeSync，与 Worker 一样调 processCombatFrame，在本线程降级执行。

---

## 第 18 页｜Worker 单帧管线（约 1 分钟）

单帧管线分三步：

**先消费**：若本帧已有 Worker 回传的 latestResult，MonsterChaseSystem 直接把速度写回各怪物 Velocity。

**同步兜底**：若没有，在主线程走 computeSync 调用 processCombatFrame，保证不阻塞可玩性。

**帧末投递**：帧末在 shouldUseWorker 为真且无在途请求时，由 dispatchCompute 向 Worker postMessage 投递下一帧计算。

这样实现了「本帧用上一帧结果、本帧末投递下一帧」，主线程与 Worker 并行分工。

---

## 第 19 页｜Worker 与对象池消融数据（约 1 分钟）

对象池消融以第 4～5 波为同窗对比，第 5 波通过 MetaRunSession.testUseCombatWorker 关闭 Worker，以隔离池化影响。解读时勿与第 3 波冷启动工况混比。

数据如下：基线（无池、无 Worker）平均 FPS 26.16，P95 76.50 毫秒；仅对象池（关 Worker）平均 FPS 25.98，P95 48.60 毫秒，P95 下降约 36.5%。

均值 FPS 接近，说明对象池主要削 GC 尖峰而非抬高平均帧率。Worker 在第 1～3 波参与追逐重算，与对象池形成互补优化路径。

## 第 21 页｜对象池设计（约 1 分钟）

对象池按预制体路径分桶复用 Laya 节点，抑制 instantiate/destroy 触发的 GC 尖峰。BulletPool、MonsterPool 按预制体路径分桶，节点用完后回池而不是销毁。

get 内部对 Map 里对应数组做 pop，拿不到节点才走 instantiate。put 会先把 node 从 parent removeChild，再 push 进桶。

适用场景：BulletSystem 生成子弹时先调 BulletPool.get；子弹寿命结束或穿透耗尽后 put 回池。MonsterRecycleSystem 判定怪物离玩家过远后 put 进 MonsterPool，控制场上活跃怪物数量。

---

## 第 22 页｜对象池实现与开关（约 40 秒）

SimpleEcsDemo 构造时注入 BulletPool 和 MonsterPool，BulletSystem 传入 isObjectPoolEnabled 作为开关回调。

isObjectPoolEnabled 为 false 时，get 被跳过，直连 instantiate，即第 4 波「无池」配置，用于同窗消融对比。MonsterRecycleSystem 回收时 put 进 MonsterPool 而不是 destroy，维持活跃集合规模。

---

## 第 23 页｜对象池实验结论（约 1 分钟）

实验数据：基线 P95 76.50 毫秒，开池 P95 48.60 毫秒，下降 36.5%；平均 FPS 从 26.16 到 25.98，变化很小。

结论有三点：

第一，池化对均值影响有限，主要削尖峰而非提均值。

第二，预热后瓶颈主要在子弹碰撞与绘制，非对象实例化。

第三，P95 显著下降验证了 GC 判断。第 3 波低于第 4 波基线，因含资源预热与首次千怪开销，消融结论以第 4～5 波为准。

另外，千怪波开启动态图集，FPS 从约 13.32 提升到约 15.10，提升约 13.4%。

## 第 24 页｜不足与展望（约 1 分钟）

## 附录 C｜评委可能提问与参考回答

### 一、选题与背景

**Q1：为什么选 H5 而不是 Unity 或 Unreal？**

A：毕设侧重验证 ECS 在浏览器单主线程环境下的可维护性与性能优化路径。H5 链接即玩、部署成本低，LayaAir 3.x 对 TypeScript 和 2D/UI2 支持完备，适合作为教学向原型载体。Unity DOTS 面向数万实体并行，与本项目「结构清晰、数百同屏」的目标不完全匹配。

**Q2：你的项目和《吸血鬼幸存者》有什么区别？**

A：战斗节奏参考类吸血鬼幸存者（自动施法、怪潮、局内构筑），元游戏参考杀戮尖塔式 DAG 跑图选关。本项目是工程原型，重点在 ECS 架构、配表驱动、性能优化和 UI 协同，不是商业级内容量。

---

### 二、ECS 架构

**Q3：ECS 和传统 OOP 继承有什么区别？你的项目里体现在哪？**

A：OOP 深继承下，新怪物常要改整条继承链；ECS 用组合表达能力——实体只是 ID，能力靠挂载组件，行为由 System 批量处理。例如玩家和怪物共用 Position、Velocity、Attribute，仅 PlayerTag/MonsterTag 不同；新怪换预制体加配表行即可，不必写子类。

**Q4：你的 ECS 是「真 ECS」吗？和 Unity DOTS 比差在哪？**

A：是轻量、教学向 ECS：单线程 Map 存储，EcsWorld.update 顺序调度，没有 Archetype/Chunk、没有 Job 并行。优势是学习成本低、与 LayaAir 集成简单；不足是同屏规模再上去时，存储和遍历效率不如 DOTS。不足与展望里也写了可演进 Archetype/Chunk。

**Q5：System 之间会不会互相干扰？执行顺序怎么保证？**

A：System 无状态，只读写组件字段。调度器按 input/logic/physics/render 分组，同组按 priority 排序。例如先 Movement 再 Bullet 再 MonsterChase，避免同一帧内读写顺序混乱。全局暂停时各 System 在 update 开头统一 return。

**Q6：FilterRegistry 是干什么的？**

A：预先注册 Players、Monsters 等筛选名，各 System 按名取实体列表，避免每帧遍历全部实体。这是性能与可读性的折中，比全量遍历好，比 DOTS 的 Archetype 查询简单。

---

### 三、配表与技能

**Q7：技能效果怎么配？modifier 和 bullet 的顺序为什么重要？**

A：技能栏位指向多条 effect 行。施法时按顺序遍历：modifier 行（分裂/连锁/穿透）只累加 pending 参数；bullet 行把 pending 写入 BulletSpawnSpec 再生成子弹；direct_damage 走公式直伤。modifier 必须在 bullet 之前，否则 pending 无法注入，会出现「有修饰无弹幕」。项目用 verify 脚本做配表回归。

**Q8：伤害公式安全吗？会不会被配表注入脚本？**

A：使用白名单公式解析器，禁止 eval，配表被篡改也不会执行任意脚本。

**Q9：配表加载失败怎么办？**

A：启动时先读注册表索引，再按表名拉取 JSON；网络 fetch 失败时改用引擎本地加载；仍失败则回退默认配置，保证能进游戏。

---

### 四、MVC 与 UI

**Q10：局内为什么还用 MVC？ECS 不够吗？**

A：元游戏（主菜单、跑图、选关）用经典 MVC；局内变体是 ECS 组件为 Model、View 为预制体节点、Controller/System 负责同步。UI 栈、页面生命周期、输入焦点适合用 Controller 管理，战斗数值仍以 ECS 为准。

**Q11：Tab 打开技能面板时，战斗怎么暂停的？**

A：SkillSelectPanelController 把 session.paused 设为 true，各战斗 System 在 update 开头检查 isPaused() 并 return。拖拽只改 SkillLoadoutState 临时对象；关面板时 SkillLoadoutSyncSystem 一次性写回 Skill 组件，再恢复 paused 为 false。

**Q12：UIStackManager 为什么需要串行化 push/pop？**

A：避免并发 push/pop 导致多面板同时 Shown、事件冲突或焦点混乱。同一时刻只有一个全屏页处于 Shown。

### 五、性能优化

**Q13：对象池为什么几乎不提升平均 FPS，却显著降低 P95？**

A：对象池减少 instantiate/destroy，降低 GC 触发频率，主要削 Scripting/GC 尖峰。平均 FPS 受子弹碰撞、绘制等主线程瓶颈制约，所以第 4、5 波均值接近（26.16 vs 25.98），但 P95 从 76.50ms 降到 48.60ms，约降 36.5%。

**Q14：Worker 做了什么？为什么碰撞还在主线程？**

A：Worker 只卸追逐、邻域排斥、摆动等纯数值计算；碰撞要读 Laya 节点位置与阵营，必须在主线程。实体数低于阈值不启用 Worker，避免 postMessage 开销。

**Q15：Worker 失败了怎么办？**

A：initWorker 失败、onerror 或 postMessage 抛错时，workerUsable 设为 false；prepareFrame 拿不到异步结果就走 computeSync，与 Worker 共用 combatWorkerLogic.ts，保证算法一致、本线程降级可玩。

**Q16：动态图集提升了多少？**

A：千怪波开启动态图集，FPS 从约 13.32 提升到约 15.10，约 +13.4%，主要降低 DrawCall 压力。

**Q17：第 3 波和第 4 波数据为什么不一样？**

A：第 3 波含资源预热与首次千怪开销，不适合做对象池消融基线。消融结论以第 4～5 波同窗对比为准：第 4 波无池无 Worker，第 5 波仅开池关 Worker。

### 六、测试与验证

**Q18：性能测试环境是什么？怎么复现？**

A：1920×1080，Level3 五波加压脚本：10 → 100 → 1000 怪观察 FPS；第 4～5 波做对象池消融。功能用例 T-F-01/05/06/09 通过；单元测试覆盖公式解析、ECS 核心、属性修饰。数据与论文第 6 章一致。

**Q19：你怎么证明优化有效，而不是偶然？**

A：对象池有开关 isObjectPoolEnabled()，第 4、5 波同窗对比，Worker 在第 5 波关闭以隔离影响。P95 降幅 36.5% 可重复，且与 Performance 面板 GC 段表现一致。

### 七、创新点与不足

**Q20：你的创新点是什么？**

A：四点：轻量 ECS 在 H5 生存战斗中的工程落地；对象池+Worker+图集+暂停早退的组合拳且可消融；Tab 与死亡共用暂停标记的 UI 战斗协同；JSON 配表+白名单公式+verify 脚本的数据驱动与可靠性（双通道加载、Worker 回退、跑图 fallback）。

**Q21：怪物 AI 用了 Boids 或社会力模型吗？**

A：没有完整社会力模型。当前是追玩家 + Boids 式邻域排斥 + 摆动，够用且可解释，不是海量人群仿真。

**Q22：项目最大不足是什么？**

A：表现层未补齐（法杖三槽 UI、部分特效音效）；架构上同屏再上去需 Archetype/Chunk 和空间哈希；测试缺 E2E UI 自动化；产品化缺局外存档和元进度。

**Q23：如果继续做这个课题，下一步做什么？**

A：优先补空间哈希降碰撞复杂度，ECS 存储改 Archetype/Chunk；补 E2E 与定期回归；产品化方向是局外存档、帧率/同屏上限设置。

### 八、可能的「刁钻」问题

**Q24：五层架构的「领域服务层」和「游戏逻辑层」边界在哪？**

A：逻辑层是每帧 ECS System 调度，是玩法唯一真相源；服务层是启动时配表加载、跑图 DAG 生成、战斗帧坐标快照桥接 Worker 等跨帧、非每帧核心的服务。逻辑层不直接操作 DOM，服务层不替代 System 的 tick。

**Q25：千怪只有 15 FPS，游戏能玩吗？**

A：原型目标是验证架构与优化路径，不是商业 60 FPS。10 怪约 58 FPS 可流畅演示；千怪是压力测试靶点，对象池改善卡顿感（P95），动态图集改善渲染，Worker 减轻追逐 CPU。产品化需要帧率上限和同屏上限设置。

**Q26：EntityId 复用会不会导致旧组件残留？**

A：销毁时组件应从 ComponentStore 移除，EntityId 进空闲列表；复用时重新挂载组件，避免脏数据。这是 ECS 实现的基本约束。
