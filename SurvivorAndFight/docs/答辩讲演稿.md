各位老师好，我是×××。今天汇报的毕业设计题目是《基于 ECS 架构的类吸血鬼幸存者游戏开发及优化》。

项目名叫 **Survivor And Fight**，是一款在浏览器里运行的 2D 俯视角生存战斗原型。技术栈采用 **LayaAir 3.x** 和 **TypeScript**。论文和工程都围绕「架构能不能撑住同屏大量实体、数值能不能靠配表迭代、性能能不能在 H5 单线程里扛住」这三个问题展开。

## 第 3 页｜研究背景与意义（约 1 分钟）

H5 游戏这几年在独立开发和教学里用得很多，链接即玩、跨端发布都方便。但浏览器里 JavaScript 往往只有一条主线程，绘制和 GC 跟逻辑抢同一帧时间。像吸血鬼幸存者这类 **Survivor-like** 玩法，同屏怪物和弹幕数量大，如果还用深继承的面向对象写法，模块容易缠在一起，后期改数值、加技能都费劲，帧率也会吃紧。

**实体组件系统 ECS** 把实体、组件数据和系统逻辑分开，用组合代替继承，比较适合这种「实体多、行为组合多」的场景。我的选题意义，就是在 LayaAir 上验证一套 **轻量 ECS + JSON 配表 + 对象池和 Web Worker** 能不能落地，并交付一个能完整跑通菜单、跑图、战斗、升级装配和死亡重启的原型。

PPT 右边这张对比表，概括了和传统 OOP 预制体方案的主要差别：扩展靠增组件而不是写子类，同屏靠池化和 Worker，数值靠改表而不是改代码。

## 第 4 页｜国内外研究现状（约 50 秒）

文献方面我主要借鉴四条线。

第一是 **引擎分层**，Gregory 和 Ullmann 的工作说明，引擎层和游戏逻辑层要划清，否则目录一嵌套深，架构就容易退化。

第二是 **ECS**，商业引擎的 DOTS 面向大规模并行，但毕设周期里我用的是 **Map 存储、单线程 tick** 的轻量实现，好上手也好查错。

第三是 **人群仿真**，Reynolds 的 Boids 和 Helbing 的恐慌模型，给怪物追逐和分离力提供了依据，对应工程里的 MonsterChaseSystem。

第四是 **验证方法**，Petty 等的 V&V 思路，落到工程里就是 `*.verify.ts` 脚本加上 Level3 五波性能实验。

中间这张脉络图，是把文献和本项目的对应关系压缩在一张里，后面几页会展开。

## 第 5 页｜项目概述与技术选型（约 1 分钟）

**Survivor And Fight** 定位是浏览器端 2D 俯视角 Roguelite 原型，不是商业成品，但要求工程上能维护、能测、能写进论文。

引擎选 **LayaAir 3.x**，原因有三：实习项目里用过，和 ECS 拆分路线一致；IDE 里能直接做 2D 预制体和 UI2，元菜单和战斗 HUD 不用另拼工具链；`frameLoop` 把主循环包好了，我只需要在每帧里调自己的 EcsWorld。

玩法上借吸血鬼幸存者的节奏和升级感，跑图参考杀戮尖塔的 DAG 选路，技能侧吸收模块化组合思路，但不做 Noita 那种像素物理。

工程上有两条硬约定：很少改的工程常量收进 `src/defines/`；会频繁迭代的策划数值放进 JSON 配表。右下角是主菜单截图，说明元游戏流程已经能进。

## 第 6 页｜需求分析概要（约 50 秒）

需求章我做了一件事：每条 Must 级需求都要能在代码或测试里找到落点。

功能上，局内要能移动、自动施法、子弹碰撞和升级奖励；局外要能选关或沿 DAG 跑图进战斗；UI 上要支持全屏栈路由、Tab 技能装配、血条同步和死亡重启。

非功能上，目标是 1920×1080 下尽量贴近 60 FPS，同屏按数百到一千实体设计，运行环境要求 Chromium、WebGL2 和 Web Worker。

可行性方面，工程不是纸面方案：ECS、配表、跑图、Tab 装配、对象池和 Worker 都有对应模块，第 7 章的五波实验也覆盖了千怪场景。中间这张图 3-1 是游戏总流程，从启动到战斗到重启的闭环在需求里写清楚了。

## 第 7 页｜系统总体架构（约 1 分 10 秒）

设计章我按六条原则组织：**数据与逻辑分离、单一职责、可验证、渐进复杂度、低耦合、可降级**。

架构上是 **五层**（请指向图 4-1）：

- **表现层**只负责 Laya 节点和 HUD，不写技能冷却这类业务规则；
- **UI 控制层**用 UIStackManager 和各类 Controller 管路由；
- **游戏逻辑层**核心是 SimpleEcsDemo 和 EcsWorld，对象池和 Worker 的优化也作用在这一层；
- **领域服务层**放配表加载、跑图生成和 MetaFlowController；
- **基础设施层**是 defines、对象池和 Worker 协议。

依赖方向是上层只依赖下层。主循环很清晰：`Laya.timer.frameLoop` 每帧先 `EcsWorld.update`，再交给引擎渲染。角标处图 2-1 是同一关系的简化版。

这样分层的直接好处是：UI 不拥有玩法真相，战斗状态以 ECS 和配表为准；性能优化有明确落点，不会散落在各处回调里。

## 第 8 页｜ECS Gameplay 设计（约 1 分 10 秒）

局内玩法走轻量 ECS（请指向图 2-2）。

**实体**用数值型 EntityId；**组件**按类型存在 ComponentStore 的 Map 里，比如 Position、Velocity、Attribute、Skill；**系统**无状态，每帧遍历实体改字段。

玩家和怪物共用位移、属性、技能组件，只靠 PlayerTag 或 MonsterTag 区分身份。FilterRegistry 预先注册 Players、Monsters 等筛选名，各 System 按名取实体，避免每个系统重复写组件交集查询。

和 Unity DOTS 比，我的方案不做 Job System 和 Burst，而是单线程顺序 tick，目标是结构清晰、支撑数百同屏，学习成本和 Laya 节点绑定成本都可控。

扩展新怪物行为时，优先加组件字段或加 System，不维护 MonsterBase 继承树——这是 ECS「组合优于继承」在工程里的具体体现。

---

## 第 9 页｜配表驱动与技能效果链（约 1 分 20 秒）

战斗数值全部 **数据驱动**。启动时 `ConfigBootstrap.ensureGameConfigLoaded()` 读 `tables.registry.json`，把各表挂进 Data.Skill 等命名空间；`isGameConfigReady()` 是能否进战斗的总闸门。

一条技能在 Skill 表占一行管冷却；具体效果拆到多行 SkillEffect。效果类型包括 bullet、三种 modifier 和 direct_damage。

这里有一张很关键的图 5-1，请各位老师看执行顺序：

- modifier 行只更新 pending 变量，不直接出子弹；
- bullet 行才把 pending 写入 BulletSpawnSpec 并生成子弹；
- direct_damage 行走 FormulaParser 公式树。

所以 **modifier 行必须写在对应 bullet 行之前**，顺序错了，局内就会出现「有修饰、没弹幕」的配置错误。伤害公式写成 `atk*1.5+10` 这类字符串，在白名单运算符内求值，工程里禁止 eval。

配表还配有 `formulaParser.verify.ts` 等脚本，改解析器后可以不进场景做快速回归。

---

## 第 10 页｜MVC UI 与战斗协同（约 1 分钟）

元游戏和局内 UI 用 **MVC 变体**：Model 来自 ECS 或跑图状态，View 只管摆位，Controller 管生命周期和路由。

全屏页走 **UIStackManager** 的 push/pop，同一时刻只有一个全屏页在前台，避免多个面板同时 visible 抢事件。

局内最有特色的是 **Tab 技能装配与战斗协同**（请指向图 5-2 时序）：

1. 玩家按 Tab，SkillSelectPanelController 把 `GameSession.paused` 置真；
2. 各战斗 System 注入 `isPaused()`，在 update 入口直接 return，怪物不再追、子弹不再出新；
3. UI 仍能吃点击，玩家长按拖拽改 SkillLoadoutState；
4. 关面板时 SkillLoadoutSyncSystem 一次性写回 Skill 和 PlayerAutoCastSystem，paused 恢复 false，新效果链在下一冷却周期生效。

跑图界面 RunMapPanelView 画 DAG，能不能走由 Model 判，View 不写通行规则——这和第 4 章「界面不拥有玩法真相」的约束一致。

## 第 11 页｜性能优化方案（约 1 分 20 秒）

H5 生存战斗的性能瓶颈，我在论文里归纳成三类：追逐和碰撞的 CPU、频繁实例化的 GC、以及绘制压力。对策是三件套，加上逻辑冻结和碰撞微优化。

**第一，对象池**（图 5-3）：BulletPool 和 MonsterPool 按预制体路径分桶，get 优先 pop，put 时 removeChild 再回池，把 instantiate/destroy 尖峰摊平。

**第二，Web Worker**（图 5-4）：场上实体数达到 `COMBAT_WORKER_MIN_ENTITY_COUNT` 后，CombatDataPrepareSystem 打包坐标快照，经 CombatDataBridge postMessage 给 Worker 算追逐、分离和摆动。主线程和 Worker **共用 combatWorkerLogic.ts**，避免两套公式。Worker 失败或未就绪时，prepareFrame 走 computeSync 主线程补算。

**第三，要注意边界**：子弹碰撞、连锁、分裂必须留主线程，因为要读 Laya 节点和阵营，Worker 里没有这套对象。

另外，`GameSession.paused` 在 Tab、死亡、胜利时让战斗 System 早退；BulletHitTest 用距离平方比较；TextureAtlasService 做动态图集合批。这几项和第 6 章实验数据一一对应。

## 第 12 页｜关键模块实现与典型场景（约 1 分钟）

实现章以 **SimpleEcsDemo 为组合根**，在构造函数里注册 System、注入 BulletPool 和 CombatDataBridge。

我重点拆三个典型场景：

**场景一，首次进战斗**：Main 先 await 配表加载，元菜单模式下 UIStack push 开始界面；玩家确认跑图或选关后，MetaFlowController 触发 onEnterCombat，显示战斗容器并 init Demo。

**场景二，Tab 换技能**：paused 切断战斗 tick，但 frameLoop 仍在跑，只是 logic 组空转；关面板后 Sync 写回，伤害变化要等下一冷却周期，这和图 5-1 顶端冷却检查是连着的。

**场景三，千怪密集**：实体够多时走 Worker 支路；关 Worker 或实体不够则 computeSync，消融实验里用同一套逻辑文件保证轨迹同源。

可靠性方面，配表双通道加载、跑图 generateFallback、重启防重入、预制体失败占位节点，都在图 4-5 时序里有对应色块。下方三张截图分别是跑图、Tab 装配和死亡重启界面。

## 第 13 页｜性能测试与数据解读（约 1 分 30 秒）

测试环境统一为 1920×1080、LayaAir IDE 内置 Chromium，Level3 五波脚本，2026 年 5 月 18 日单次运行。

请看左边这张五波 FPS 柱图（表 7-5）：怪物从 10 到 100 再到 1000，FPS 从 58.62 降到 15.14，符合实体和弹幕压力上升的规律。整场平均约 34.48 FPS，因为后面几波拉低了均值。

**动态图集**（表 7-4）：第 3 波千怪场景，接入 TextureAtlasService 后，FPS 从 13.32 提到 15.10，大约 **提升 13.4%**，说明合批主要改善绘制侧。

**对象池消融**（表 7-6，请指向右边 P95 对比图）：第 4、5 波都是 1000 怪、同窗对比。关池时 P95 帧时间 76.50 毫秒；开池后降到 48.60 毫秒，约 **降低 36.5%**。平均 FPS 几乎不变，说明池化主要削的是 GC 和实例化带来的 **尖峰卡顿**，不是拉高均值。

解读时有两点要注意：第 3 波含首次千怪冷启动，不宜和第 4、5 波消融直接比；第 4、5 波关 Worker 是为了隔离池化影响。

## 第 15 页｜主要创新点与工程特色（约 50 秒）

工程侧我总结五条特色：

1. **轻量 ECS**：EcsWorld 驱动 tick，ViewComponent 只绑节点，业务尽量不直接调引擎 API。  
2. **性能组合拳**：池、Worker、图集、paused 冻结都可开关，方便消融和对照。  
3. **UI 与战斗协同**：Tab 装配和死亡暂停共用 `GameSession.paused`，避免 UI 和玩法各维护一套 pause。  
4. **数据驱动 + 可验证**：JSON 配表配合 verify 脚本和需求—测试映射表，改底层有据可查。  
5. **可靠性设计**：配表、Worker、跑图、预制体都有降级路径，尽量不让整局白屏。

右边竞品对比表强调的是：一般 H5 Demo 停在预制体加 OOP；本项目把架构、配表和性能优化做成一套可写进论文、可复现实验的工程闭环。

## 附录 B：常见问题预备答复（供 Q&A 参考，不上台念）

**Q1：为什么不用 Unity DOTS 或完整 ECS 框架？**  
A：毕设周期和 Laya 节点绑定成本有限；Map + 单线程 tick 的轻量 ECS 已支撑数百同屏，且 verify 脚本好回归。论文表 2-2 有对比。

**Q2：Web Worker 为什么不把碰撞也放进去？**  
A：Worker 不能访问 Laya 节点和 DOM；子弹碰撞要读节点位置、阵营和当帧命中，必须主线程。Worker 只卸载追逐、分离等纯数值计算，且与主线程共用 combatWorkerLogic.ts。

**Q3：对象池为什么主要改善 P95 而不是平均 FPS？**  
A：表 7-6 同窗对比显示均值接近，但 P95 从 76.50 ms 降到 48.60 ms；池化减少的是 instantiate/destroy 触发的 GC 尖峰，对偶发卡顿更明显。

**Q4：Tab 暂停为什么不用直接停 frameLoop？**  
A：停 frameLoop 会连 UI 输入和渲染一起停；现在做法是 frameLoop 照跑，战斗 System 因 `GameSession.paused` 早退，UI 仍可响应，生存计时也可单独 pause。

**Q5：配表 404 或没同步怎么办？**  
A：开发阶段用 sync-config-to-bin.ps1；运行时 isGameConfigReady() 拦在未就绪前进战斗；缺表键 missingConfigLogged 只告警一次并回退 defines 默认值。

**Q6：DAG 跑图生成失败怎么办？**  
A：RunMapGenerator 随机重试后若 Boss 仍不可达，走 generateFallback 线性保底图，避免局外进度卡死。
