## 摘要

**关键词**：游戏引擎；耦合；影响分析；受控实验

游戏引擎是帮助加速视频游戏开发的工具。它们提供图形、声音和物理仿真功能，这些功能原本需要由开发人员自行实现。尽管对于现代商业视频游戏开发来说至关重要，但游戏引擎结构复杂，开发人员往往难以理解其架构，从而导致维护和演化问题，对视频游戏制作产生负面影响。在本文中，我们提出了子系统依赖恢复方法（SyDRA），它帮助游戏引擎开发人员理解游戏引擎架构，从而做出明智的游戏引擎开发决策。通过将这种方法应用于10个开源游戏引擎，我们获得了可用于比较游戏引擎架构并识别和解决过度耦合和文件夹嵌套问题的架构模型。通过一项有16名参与者参与的受控实验，我们表明，与没有这些模型相比，检查由SyDRA派生的架构模型使开发人员能够以更短的时间和更高的正确性完成与架构理解和影响分析相关的任务。

## 1. 引言

游戏引擎是帮助加速视频游戏开发的工具。它们提供开箱即用的功能，这些功能足够广泛，可用于创建各种视频游戏，例如图形渲染、声音管理和物理仿真。从头开发游戏引擎既昂贵又耗时，只有大型视频游戏公司才能负担得起。虽然存在风险，但这种努力带来了优化特定类型游戏或游戏 genres 的工具的可能性。此外，通过创建内部解决方案，公司可以避免支付许可费用，同时可以自由地向他人许可其技术，例如CryEngine和IdTek最近所做的那样。

然而，开发游戏引擎的优势只有在理解其结构的情况下才能持续。随着时间的推移，开发团队因高离职率而变化，游戏引擎代码库也会发生变化，导致其偏离原始结构，这一过程称为架构漂移或侵蚀。此外，由于需要创新和尝试不同的视频游戏，公司有时会决定通过在遗留架构之上开发新功能来重新调整其游戏引擎的用途。在这种情况下，缺乏对核心游戏引擎代码原始架构的理解会导致维护和演化问题。以下是2019年Bioware用于开发Anthem的Frostbite游戏引擎的开发人员报告的这类问题的一个例子：

"Frostbite就像一款自带所有问题的内部引擎——文档糟糕、临时拼凑等等——以及外部引擎的所有问题，"一位前BioWare员工说。"实际上没有人设计它，所以你不知道这个东西为什么以这种方式工作，为什么以这种方式命名。"

缺乏对游戏引擎架构的理解阻碍了开发人员维护和演化它的能力，严重影响游戏开发项目的进度。例如，将Frostbite重新用于Dragon Age: Inquisition"占用了项目开发时间的大约三分之一"。同样，Bethesda的开发人员在为单人游戏专门制作的Creation Engine中添加了多人游戏支持。在Fallout 76开发过程中，这个功能导致了一些bug，并"给进度带来了额外的时间压力"。因此，我们可以说架构理解影响了视频游戏开发的技术和管理两个方面。

虽然Frostbite和Creation Engine开发人员报告的问题反映了闭源游戏引擎开发的现实，但类似的问题也可以在开源游戏引擎中观察到。尽管Unreal和Godot等游戏引擎维护官方文档和支持论坛，但这些数据源主要专注于为视频游戏开发人员提供"入门"的方式，解释如何使用游戏引擎的功能，同时隐藏其实现的底层方面。因此，希望重新调整游戏引擎用途或选择最适合自己的游戏引擎的游戏引擎开发人员不能仅依赖这些文档。他们必须深入研究代码，学习其结构，最后将其与其他游戏引擎的结构进行比较，以做出明智的游戏引擎开发决策。

在本文中，我们使用子系统依赖恢复方法（SyDRA），该方法在我们之前的工作中描述过，帮助游戏引擎开发人员理解游戏引擎架构，从而做出明智的游戏引擎开发决策。通过将SyDRA应用于10个开源游戏引擎，我们获得了可用于比较游戏引擎架构并识别和解决高耦合和低内聚等问题的架构模型。通过一项有16名参与者参与的受控实验，我们表明，与没有这些模型相比，检查由SyDRA派生的架构模型使开发人员能够以更短的时间和更高的正确性完成与架构理解和影响分析相关的任务。

SyDRA的实现和评估使我们能够回答以下研究问题：

- **RQ1**：与仅仅检查代码相比，SyDRA是否能帮助开发人员更有效地理解游戏引擎？
- **RQ2**：与仅仅检查代码相比，SyDRA是否能帮助游戏引擎开发人员更有效地执行游戏引擎影响分析？

我们对这两个问题都给出了肯定的答复，并得出结论：通过使用SyDRA，开发人员可以更好地理解游戏引擎架构，而不会增加他们的感知工作量。我们的实验还提供了关于开发人员如何感知软件分析工具中的工作量及其与专业经验之间关系的见解。

本文的结构如下。第2节介绍了软件架构和游戏引擎的相关工作。第3节提供了SyDRA的高层描述，我们的软件架构恢复方法，以及如何用它生成10个开源游戏引擎的架构模型。第4节描述了由SyDRA产生的架构模型如何帮助游戏引擎开发人员解决文件夹组织和耦合问题，以及做出游戏引擎开发决策。第5节描述了用户研究的设计和执行及其结果。第6节介绍了内部和外部有效性威胁，第7节给出了结论和未来工作。

## 2. 相关工作

游戏引擎的结构和目的往往没有很好的文档记录，因此 several researchers 尝试使用软件架构恢复技术来搜索源代码中的架构结构，并帮助开发人员赋予它们意义。例如，Munro等人（2009）使用Doxygen（一个流行的文档生成工具）从开源版本的IdTech游戏引擎提取依赖信息。这些数据然后被用于创建依赖图，有助于"识别特定引擎的合适改进和增强的过程，并以适当的方式支持这些改进的实现"。

Agrahari和Chimalakonda（2021）开发并使用了AC²，这是一个"为Unreal Engine的三个版本生成调用图和协作图"的软件分析工具。这些图帮助他们识别组件中的架构模式，观察它们的演化，"帮助研究人员和从业者更好地理解这个复杂且广泛使用的游戏引擎"。

研究人员进行实验来评估提取的架构模型的有用性。在这些研究中，他们向开发人员展示了一组架构理解任务。通过测量开发人员在有或没有支持架构模型或文档的情况下执行任务的速度和正确性，他们评估该模型对系统理解带来的好处。在第5节中，我们描述了我们如何根据Briand等人（2001）的工作设计和进行受控实验。

或者，研究人员可以进行实地研究，观察开发人员和架构师如何在真实场景中使用它们。然而，这种研究需要与公司合作和长期观察。考虑到视频游戏和游戏引擎开发的封闭源代码性质，这对于我们的研究来说不是一个可行的选择。正如我们在第3节中解释的，SyDRA依赖于对源代码和文档的分析，两者都必须公开可用。

## 3. 方法

子系统依赖恢复方法（SyDRA）由六个步骤组成，如图1所示，它帮助游戏引擎开发人员分析一个或多个游戏引擎。SyDRA的步骤描述了开发人员如何一致地选择要分析的游戏引擎，如何将它们的文件和文件夹聚类，以及如何将此信息与包含图进行交叉引用。结果，他们获得了可用于理解游戏引擎架构结构、识别和减少过度耦合以及提高内聚性的架构模型。

![图1：我们游戏引擎分析方法的步骤](图1)

我们在GitHub上提供了SyDRA的实现，以及我们对10个开源游戏引擎进行分析产生的数据和可视化，我们也在之前的工作中展示和讨论了这些结果。我们通过如下实现SyDRA的步骤来获得这些结果：

### 3.1 系统选择

我们从GitHub中选择10个开源游戏引擎，搜索"game engine"关键字，按C++语言筛选，然后按流行度排序结果。我们认为流行度是仓库中GitHub星标的数量。我们选择这个指标是因为它是"仓库包含工程软件项目的部分证据"。这样，我们避免了选择不能正确代表工业级游戏引擎规模和复杂性的"玩具"项目。

### 3.2 子系统选择

对于每个选定的游戏引擎，我们定义了如何将每个文件和文件夹聚类为功能组，即子系统。我们考虑了Jason Gregory（2018）在"Runtime Game Engine Architecture"中描述的16个 subsystems，每个对应创建大多数视频游戏所需的常见功能。例如，图形、音频、物理仿真和输入设备处理。我们在表1中总结了这个subsystems列表。

| ID | 子系统 | 描述 |
|---|---|---|
| AUD | Audio | 管理音频播放和效果 |
| COR | Core | 管理引擎初始化，包含数学、内存分配等库 |
| DEB | Profiling & Debugging | 通过游戏内菜单或控制台管理性能统计和调试 |
| EDI | World Editor | 支持可视化游戏世界构建 |
| FES | Front End | 管理GUI、菜单、平视显示器(HUD)和视频播放 |
| GMP | Gameplay Foundations | 管理游戏对象模型、脚本和事件/消息系统 |
| HID | Human Interface Devices | 管理游戏特定输入接口、物理I/O设备 |
| LLR | Low-Level Renderer | 管理相机、纹理、Shader、字体和一般绘制任务 |
| OMP | Online Multiplayer | 管理匹配制作和游戏状态复制 |
| PHY | Collision & Physics | 管理力和约束、刚体、射线/形状投射 |
| PLA | Platform Independence Layer | 管理平台特定图形、文件系统、线程等 |
| RES | Resources | 管理游戏资源（如3D模型、纹理、字体）的加载/缓存 |
| SDK | Third-Party SDKs | 支持与DirectX、OpenGL、Havok、PhysX、STL等的接口 |
| SKA | Skeletal Animation | 管理动画状态树、逆向运动学(IK)和网格渲染 |
| SGC | Scene Graph/Culling Optimisations | 计算空间哈希、遮挡和细节级别(LOD) |
| VFX | Visual Effects | 支持光照贴图、动态阴影、粒子、贴花等 |

### 3.3 子系统检测

对于每个选定的游戏引擎，我们手动将所有文件和文件夹聚类到选定的子系统中。为了确保实现相同功能的文件被聚类到同一组，我们考虑它们的命名、文件夹层次结构、文档中的提及以及源代码中的注释来确定它们的功能。

我们将SyDRA的步骤应用于10个开源游戏引擎大约花了六个月的时间。最耗时的步骤是子系统检测（步骤3），由第一作者专门执行，大约花了两个月的时间。在第4节中，我们展示了由SyDRA应用产生的架构模型。此外，在第5节中，我们展示了架构模型的使用如何为执行架构理解和影响分析任务的开发人员提供信息的示例。

作为应用SyDRA的结果，我们获得了10个架构模型，每个选定的游戏引擎一个。这些模型是图，其中每个节点是一个文件，每条边是文件之间的包含关系。例如，使用架构图，我们可以查看Godot中包含"camera"一词的文件。

## 4. 架构模型的应用

作为应用SyDRA的结果，我们获得了10个架构模型，每个选定游戏引擎一个。这些模型是图，其中每个节点是一个文件，每条边是文件之间的包含关系。

### 4.1 子系统耦合

通过SyDRA获得的架构模型，我们能够识别最常耦合的子系统对。表2显示了我们分析中看到的最常见的子系统耦合对。

| Pair | Count |
|---|---|
| COR → LLR | 9 |
| GMP → COR | 9 |
| LLR → COR | 9 |
| PHY → COR | 9 |
| COR → RES | 8 |
| FES → COR | 8 |
| RES → COR | 8 |
| SKA → COR | 8 |
| LLR → RES | 8 |
| SKA → LLR | 8 |

Core（COR）、Low-Level Renderer（LLR）和Resources（RES）是最频繁耦合的子系统。如表1所示，这些子系统有几个职责，我们认为这是它们高耦合的原因。例如，Low-Level Renderer（LLR）子系统不仅仅是简单地绘制在屏幕上，还提供虽然与视觉相关但也与其他子系统相关的抽象。例如，虽然相机功能是LLR的一部分，但为了知道相机的视野范围内有什么以及需要绘制什么，它依赖于Scene Graph/Culling Optimizations（SGC）子系统，后者提供遮挡和遮挡计算。

### 4.2 文件和子系统耦合

检查文件之间的包含关系以及将其与游戏引擎文档（如果存在）进行交叉引用，可以深入了解子系统特定部分的工作方式。例如，我们检查了Panda3D和GamePlay3d中的子系统。

例如，如果我们查看Panda3D的Low-Level Renderer（LLR）子系统，我们观察到它具有很高的入度，这是因为它的display文件夹，其中包含实现图形相关功能的文件，供Scene Graph/Culling Optimizations（SGC）和Visual Effects（VFX）子系统使用。例如，这些文件之一graphicsStateGuardian.h实现了一个图形状态守护者（GSG），它接收高级渲染指令（例如绘制场景图中存在的角色），然后以操作系统和图形硬件可以理解的格式处理低级渲染指令。

### 4.3 紧急游戏引擎架构

正如在第4节中所展示的，开发人员可以通过可视化和分析游戏引擎架构模型来识别架构问题并思考解决方案。虽然分别分析游戏引擎很有用，但我们也可以组合不同游戏引擎的模型，以观察从这个组合中出现哪些架构模式，因此是所分析集合中所有游戏引擎共有的模式。

例如，在图9中，我们使用箱线图来表示在我们分析的10个游戏引擎中子系统之间最常见的关系。在图的中心，我们放置了具有最高介数中心性的子系统，形成内层核心（深红色）。接下来，我们放置了出现在表2中的其他子系统在外层核心（浅红色）。最后，我们将未出现在表2中的子系统放在外层核心的周围（白色）。图中显示的所有关系都是最常见的，如表2所示。当存在平局时（例如两对的频率相同），我们选择介数中心性总和最高的耦合对。

在这种紧急架构中，我们观察到Low-Level Renderer（LLR）经常与Core（COR）相互依赖，COR用它来访问Platform Compatibility Layer（PLA）和Resources（RES）的功能。它经常被World Editor（EDI）和Gameplay Foundations（GMP）包含，两者都是用户与游戏引擎之间的视觉接口。因为它管理发出事件并在整个系统中触发操作的UI元素，Front End（FES）经常依赖Core（COR）中的事件/消息系统。

通过提供子系统包含的高层视图，我们在这里展示的紧急游戏引擎架构可以为希望构建结构上类似于我们所分析的游戏引擎集合的新游戏引擎的游戏引擎开发人员提供架构参考。它也可以作为分析现有游戏引擎的指南，显示如果更改任意数量的其他子系统，哪些子系统可能受到影响。

### 5.1 假设

零假设陈述如下：

- **H₀**：使用SyDRA对游戏引擎架构的可理解性和可维护性没有显著差异。

### 5.2 参与者

我们招募了16名参与者，所有人都在18岁以上且有面向对象编程经验。我们通过电子邮件或亲自询问来招募他们。大多数参与者是30岁以下、位于巴西或加拿大的男性。他们主要是学生、研究人员或视频游戏行业外的软件开发人员。他们大多有2到5年的软件开发经验，并曾将Unity用于学生或业余项目。

参与者对游戏引擎使用和开发的熟悉程度差异很大。例如，虽然57%的参与者报告没有游戏引擎经验，但有两名参与者报告开发了自己的游戏引擎。这种经验水平的多样性很重要，因为它使我们能够观察我们为研究选择的工具如何被不同类型的开发人员使用以及他们面临的挑战。更多详细的人口统计细分可以在我们研究小组网站上发布的复制包中找到。

### 5.3 材料

在本研究中，参与者分析了Godot，这是一个由Juan Linietsky和Ariel Manzur于2014年发布的跨平台、免费和开源游戏引擎。我们选择Godot是因为它在GitHub上的开源开发者社区中的相关性，如第3节所述。虽然控制组参与者专门使用Visual Studio Code来分析Godot的源代码，但治疗组参与者同时使用Moose + Visual Studio Code，因此可以访问由SyDRA生成的Godot架构图可视化。

我们创建了教学文档来教参与者如何使用给定的工具。正如我们在第5.5节中解释的，我们要求参与者在执行任务之前阅读与他们即将使用的工具相关的文档。这些文档提供了文件搜索和浏览等功能概述，并配有截图。在每份文档的最后，我们还提供了三个可选的热身练习，旨在强化指令。尽管类似于实验中的任务，但这些热身更简单，一次专注于一个功能。例如，在Visual Studio Code热身中，我们要求参与者使用搜索功能查找并计算包含"Music"一词的文件数量。他们可以验证文档最后一页的答案。

在本节中，我们提供了Moose和Visual Studio Code的主要功能概述，以及我们选择这些工具进行研究的理由。我们还描述了参与者在实验中为帮助完成任务而使用的功能，并展示了教学文档中包含的截图示例。

**Moose**：一个由Pharo编程语言构建的软件分析平台。它使用户能够定义元模型并基于它们创建模型。它还允许用户将这些模型可视化为架构图，如第3节所解释的。模型实体可以写入（或用Moose的行话说"传播"到）总线，这是工具之间的通信通道。Moose工具（如架构图）然后可以读取这些实体。

**Visual Studio Code**：一个由Microsoft开发的源代码编辑器，支持调试、语法高亮、智能代码完成、代码片段、代码重构和嵌入Git。

### 5.4 任务

我们向参与者展示了7个架构理解任务和2个影响分析任务。我们还根据不同组的参与者必须执行的步骤调整了任务陈述，以在他们使用的工具中找到文件。例如，在任务2中，当我们要求治疗组参与者"展开Audio子系统"然后"传播"给定文件时，我们要求控制组参与者按名称搜索文件然后打开它。这样，我们确保两个参与者被引导到同一个文件，即使他们遵循不同的步骤来查找和打开它。

**任务陈述示例**：

| 类型 | 控制组 | 治疗组 |
|---|---|---|
| 架构理解 | 搜索文件servers/audio/audio_effect.h并打开它。提供其功能的简短描述。 | 展开Audio子系统，展开"audio"文件夹并传播文件servers/audio/audio_effect.h。提供其功能的简短描述。 |
| 影响分析 | 假设Godot的Front End子系统的富文本功能被移除。请提及由于这些功能移除可能需要更改的所有文件。 | 假设Godot的Front End子系统的富文本功能被移除。请提及由于这些功能移除可能需要更改的所有文件。 |

### 5.5 实验执行

研究会议分为三个部分。首先，我们要求参与者阅读并遵循第5.3节中描述的教学文档。然后，我们要求他们执行任务。最后，参与者完成了一份汇报问卷，我们在其中询问了他们的背景信息以及对他们执行任务的工作量评估。对于第二和第三部分，参与者通过在线表单提交了答案，该表单还计算了答案之间经过的时间。

汇报问卷分为两部分。在问题1到7中，我们询问了参与者的专业背景和人口统计。在问题8到13中，我们要求参与者根据NASA TLX（任务负载指数）问卷对他们执行任务的工作量进行评估。我们选择NASA TLX是因为它在评估软件开发、界面设计和决策活动的研究中已被使用了20多年。

在研究会议期间，我们全程为参与者提供支持，但与他们保持身体距离。我们的支持仅限于在询问时澄清任务描述以及解决与研究相关的计算机和工具的技术问题。

### 5.6 测量

我们通过测量他们花在任务上的时间以及他们完成任务正确与否来衡量参与者对游戏引擎架构理解的水平。我们从这些数据中派生出六个因变量，与原始实验相同：

- **UndTime**：花在架构理解任务上的时间（分钟）
- **UndCorr**：架构理解任务的正确性（例如，正确回答的任务数量）
- **UndTime**：花在影响分析任务上的时间（分钟）
- **ModComp**：影响分析的完整性，通过参与者告知的正确文件数除以实际正确文件数获得
- **ModCorr**：影响分析的正确性，通过参与者告知的正确文件数除以参与者告知的总文件数获得
- **ModRate**：修改率，通过参与者告知的正确文件数除以ModTime获得

原始研究没有定义架构理解正确性，所以我们将其定义为二元的：答案要么正确（1）要么错误（0）。因此，UndCorr的范围从0到7，因为总共有7个架构理解任务。对于影响分析任务，正确性定义为参与者正确告知的文件数除以他们告知的总文件数的比率。因此，ModCorr的范围从0到2，因为总共有两个影响分析任务。

### 5.7 数据分析程序

我们在一个月的16次会议中收集了参与者的数据。因此，控制组有8个数据点，治疗组有8个数据点。所有参与者都回答了所有任务和汇报问题。我们使用以下统计技术来确定研究期间收集的数据是否具有统计显著性：

1. **参与者数量**：我们使用两样本T检验来确定我们需要多少参与者才能检测到统计显著差异。我们考虑了α = 0.05，统计功效为0.9，并根据原始实验的标准差。对于任务完成时间，我们定义了最小差异1分钟。对于任务正确性，我们定义了最小30%差异。总数至少需要14名参与者。我们通过进行16名参与者的研究来超过这个数量，以确保统计显著性。

2. **正态性**：我们使用了Kolmogorov-Sirnov和Shapiro-Wilks'W正态性测试。在这两种情况下，我们观察到所有因变量都呈非正态分布。

3. **统计显著性**：我们使用了适合非正态数据的非参数显著性检验，即Wilcoxon匹配对检验。为了显著，检验的结果（称为Z值）必须超过α = 0.05、单尾的临界Z值，如Wilcoxon符号秩表所示。我们观察到UndTime、UndCorr、ModCorr和ModRate超过了临界Z值，而ModTime和ModComp没有。

4. **效应大小**：我们通过计算控制组和治疗组算术平均值之间的差异，然后除以控制组和治疗组标准差的几何平均值，来计算每个变量的效应大小。

### 5.8 结果

表5显示了我们从研究的16名参与者收集的因变量的摘要。列表示均值(X)、中位数(m)、最小值和最大值以及标准差(s)。平均而言，参与者花了62分钟完成理解任务，31分钟完成影响分析任务，总共1小时33分钟。从标准差，我们观察到完成时间和正确性都有很高的可变性，反映了参与者不同的经验水平。

通过观察与时间（UndTime）和正确性（UndCorr）相关的变量，我们可以理解每个组使用的工具如何影响参与者在架构理解任务中的表现。虽然治疗组更快地完成了任务，但两组以相同的正确性水平完成了任务。因此，使用SyDRA减少了任务完成时间，但对任务正确性没有影响。

在影响分析任务中，控制组完成任务更快但正确性低于治疗组。这是因为通过专门使用VS Code，参与者在查找文件之间所有传出和传入的包含关系时遇到了更多困难，并过早结束了他们的分析。相比之下，使用SyDRA的参与者可以将关系简洁地可视化为架构图中的箭头，这帮助他们更正确地完成影响分析。

然而，在解释这些结果时，我们还必须考虑统计显著性和效应大小。例如，虽然UndTime、UndCorr和ModCorr具有统计显著性，但ModTime不是，这意味着在研究中观察到的平均影响分析时间不能推广。此外，我们没有为任何统计显著的变量识别到大效应大小，如表6所示。根据软件工程中定义的规模，统计显著变量的最大效应大小是ModCorr的"中等"。

**受控实验结论**：

基于我们的观察，我们接受H₁和H₂。结果表明，使用SyDRA可以在不影响任务正确性的情况下实现任务完成时间的统计显著减少。关于影响分析，使用SyDRA导致任务正确性略高，但任务完成时间没有统计显著差异。

### 5.9 讨论

在图13中，我们比较了参与者关于NASA TLX问卷描述的任务负载的六个方面的答案：心理、体力和时间需求、成功感知、努力和挫败感。关于成功感知和时间需求，各组之间没有差异，这证明了参与者使用的工具没有让他们感到不堪重负。

我们还观察到参与者的成功感知与他们的经验水平相关。例如，视频游戏开发人员报告了更高的成功感知、更低的心理需求和更低的挫败感，比非视频游戏开发人员和学生/研究人员。我们在比较所有背景的新手（少于5年专业经验）和经验丰富（5年或以上专业经验）开发人员时也观察到相同的模式。

与控制组相比，治疗组报告了更低的心理需求、努力感知和挫败感，这证明了参与者在使用VS Code与SyDRA生成的架构模型时比单独使用VS Code更舒适。相比之下，治疗组报告了比控制组更高的体力需求。然而，体力需求不是软件开发中工作量的主要贡献者。因此，我们认为这些高体力需求的报告不一定证明使用SyDRA比单独使用VS Code需要更多的身体运动或努力。

总体而言，我们通过NASA TLX问卷收集的数据表明，参与者在使用SyDRA时感知到更低的任务负载，尽管这种感知与每个参与者的专业经验和视频游戏领域的熟悉程度相关。我们观察到各组之间最大的差异是在任务心理需求和挫败感的感知方面。

## 6. 有效性威胁

在本节中，我们讨论SyDRA和受控实验的有效性威胁。

### 6.1 外部有效性

我们承认，我们为使用SyDRA分析选择的游戏引擎可能无法完全代表所有开源游戏引擎或整个视频游戏行业。我们通过根据流行度选择游戏引擎来缓解这个问题，如第3节所述。我们将分析限制在C++游戏引擎，这可能导致排除用其他编程语言开发的相关游戏引擎。

此外，我们承认在所有游戏引擎中使用"Runtime Game Engine Architecture"进行子系统检测可能会引入偏见。作为缓解策略，在未来工作中，我们打算涵盖更广泛的子系统范围，既通过SyDRA获得，也通过游戏引擎开发文献获得。

在受控实验中，我们使用了2×1设计，而不是被试内设计，这不同于原始的2×2被试内设计。我们选择这种设计是因为有限的参与者可用性，这使得确保所有参与者可以两次参与研究变得困难或有时不可能。正如原始实验中所解释的，通过使用2×2被试内设计"减少了由于受试者差异导致的误差方差"。我们知道通过选择2×1设计，我们有风险为所有因变量获得更高的误差方差。在未来工作中，我们打算进行更多参与者的另一项研究，并使用2×2被试内设计。

此外，混淆效应可能来自我们为受控实验选择的游戏引擎、分析工具和参与者。例如，Godot可能无法代表所有开源游戏引擎的规模和复杂性。此外，大多数参与者没有视频游戏开发经验，因此不能准确代表这些领域的开发人员。最后，我们没有为任何统计显著的因变量检测到大效应大小，这证明我们的结果可能无法推广到其他游戏引擎或更多样化的参与者。

### 6.2 内部有效性

SyDRA的子系统检测步骤由第一作者手动执行，这可能在过程中引入了偏见。为了缓解这个问题，我们打算分配多个人在此步骤中工作，然后通过共识结合他们的结果。我们还打算探索子系统检测的准自动化方法，以确定最适合游戏引擎和其他类型软件的方法。

此外，我们意识到我们对SyDRA结果的分析依赖于Moose行为，以及我们从架构模型中提取的图指标（例如入度和中心性）。改变它们也可能改变结果，因此改变我们对这些游戏引擎架构的看法。在未来工作中，我们打算尝试不同的软件分析和可视化工具，并测量它们在多大程度上可以帮助开发人员执行架构理解、影响分析和测试活动。

在受控实验的背景下，虽然我们测量了参与者完成理解和影响分析任务的速度和正确性，但我们没有测量他们是否也能够快速且正确地在源代码中实现更改。此外，虽然任务允许几种可能的解决方案，但我们没有验证参与者提供的解决方案是否是最佳或最优化的，而只是验证它是否在架构上合理。

我们知道大多数任务陈述和汇报问卷允许多种解释，这可能是我们在任务完成时间和任务正确性方面观察到的大变化的原因。观察者效应也可能导致了这种变化，考虑到如果他们没有被观察到，参与者可能会感到压力较小或行为不同。正如我们在第5.5节中解释的，我们通过与参与者保持身体距离并仅在必要时与他们互动来试图缓解这种效应。

成熟效应可能发生在研究过程中，因为参与者了解了工具的工作方式。一些参与者也有使用研究中工具的先验经验，这可能帮助他们比其他人更快、更正确地完成任务。正如我们在第5.3节中所述，我们通过选择大多数开发人员熟悉的工具（Visual Studio Code）以及为两种工具提供教学文档来缓解这种效应。

仪器效应也可能由于控制和治疗任务描述之间的差异而产生。正如我们在第5.4节中解释的，我们尽最大努力确保任务可以用两种工具相似的努力量完成，任务描述清晰并以相同的方式陈述给两组。然而，这些差异也可能影响了参与者理解和更正确完成任务的能力。

## 7. 结论

在本文中，我们提出了子系统依赖恢复方法（SyDRA）。通过将这种方法应用于10个开源游戏引擎，我们获得了可用于比较游戏引擎架构并识别和解决高耦合和低内聚等问题的架构模型。此外，我们展示并讨论了从架构模型派生的指标和可视化如何帮助游戏引擎开发，例如：

- **架构理解**：架构模型可视化，为新手游戏引擎开发人员提供了理解这类系统的友好方式，并开始开发自己的子系统或插件。此外，我们在第5.8节展示了架构模型的使用如何帮助架构理解。
- **影响分析**：游戏引擎开发人员可以通过可视化子系统更改如何影响整个游戏引擎来更安全地重构代码。
- **参考提取**：寻求设计新引擎的游戏引擎架构师可以从类似系统中提取架构模型并将其用作参考。他们可以提取和可视化单个系统的数据，或者将同一家族中多个系统的数据连接起来，如图9所示。这对大型公司和为性能开发定制解决方案的小型独立开发人员都很有用。

通过与16名软件开发人员进行的受控实验，我们评估了SyDRA在多大程度上帮助开发人员执行架构理解和影响分析任务。我们要求开发人员分析Godot，这是一个开源游戏引擎。虽然控制组参与者专门使用VS Code分析Godot的源代码，但治疗组参与者同时使用Moose + Visual Studio Code，因此可以访问由SyDRA生成的Godot架构图可视化。我们实验最重要的贡献是表明在使用VS Code与SyDRA生成的架构模型时，架构理解任务的完成时间有小幅但统计显著的减少。

最后，我们对实验汇报问卷答案的分析表明，通过使用SyDRA，开发人员可以更好地理解游戏引擎架构，而不会增加他们的感知工作量。在未来工作中，我们打算要求游戏引擎开发人员评估我们关于子系统耦合减少（第4.1节）和子系统内聚增加（如第4.2节所示）的建议，以及我们在第4.4节中提出的紧急游戏引擎架构。我们的目标是了解这些建议在专业视频游戏开发环境中是否有用，我们将寻求与独立视频游戏开发公司合作来实现这一目标。

此外，我们意识到SyDRA足够灵活，可用于分析对视频游戏制作 fundamental 的其他软件系列，例如图像和声音编辑器以及3D建模软件。因此，我们打算将SyDRA应用于这些软件系列，以识别可以指导其创建、维护和演化的共同架构结构。
